@topic a11y-semantic-html
title: HTML semantyczny
level: mid
tags: semantic HTML, button, nav, main, article
summary: Semantyczny HTML to znaczniki opisujące znaczenie treści, a nie tylko jej wygląd. Daje darmową dostępność, lepsze SEO i czytelniejszy kod.

::: body
Przeglądarka buduje z DOM **drzewo dostępności (accessibility tree)**, z którego korzystają czytniki ekranu. Semantyczny element niesie w nim **rolę**, **nazwę** i **stan** bez żadnego dodatkowego kodu.

- `<button>`: fokusowalny, działa z Enter i Spacją, ogłaszany jako przycisk. `<div onClick>` nie ma żadnej z tych cech.
- `<a href>`: nawigacja (zmiana URL). `<button>`: akcja na stronie. Nie mieszaj.
- Struktura: `<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>`, `<section>` (z nagłówkiem), `<article>` (samodzielna treść, np. karta oferty).
- Formularze: `<form>`, `<label>`, `<fieldset>` + `<legend>` dla grup (np. radio), właściwe `type` inputów (`email`, `tel`, `date`) i `autocomplete`.
- Listy `<ul>/<ol>`, tabele danych `<table>` z `<th scope>` i `<caption>`.
- Natywne komponenty: `<dialog>`, `<details>/<summary>`, atrybut `popover`.

Zyski: dostępność "za darmo", SEO (wyszukiwarki rozumieją strukturę), obsługa klawiatury, mniej JS, łatwiejsze testy (Testing Library szuka po rolach).

::: code html
<!-- Bad: div soup -->
<div class="btn" onclick="book()">Rezerwuj</div>

<!-- Good -->
<article class="offer">
  <h2>Kreta, Hersonissos</h2>
  <p>7 nocy, all inclusive</p>
  <button type="button" onclick="book()">Rezerwuj</button>
</article>

<details>
  <summary>Warunki anulacji</summary>
  <p>Bezpłatna anulacja do 30 dni przed wylotem.</p>
</details>

::: qa
Q: Czym jest semantyczny HTML i dlaczego jest ważny?
A: Używaniem znaczników zgodnie z ich znaczeniem (`button`, `nav`, `main`, `article`, `label`). Elementy te mają wbudowane role, obsługę klawiatury i stany, co daje dostępność dla czytników ekranu, lepsze SEO i mniej kodu JS.
Q: Kiedy <a>, a kiedy <button>?
A: `<a href>` gdy przenosisz użytkownika w inne miejsce (zmiana URL, może być otwarty w nowej karcie). `<button>` gdy wykonujesz akcję na bieżącej stronie (otwarcie modala, wysłanie formularza, dodanie do koszyka).

::: sources
- MDN Glossary: Semantics (in HTML) | https://developer.mozilla.org/en-US/docs/Glossary/Semantics#semantics_in_html
- MDN: HTML: A good basis for accessibility | https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML
- web.dev: Learn Accessibility | https://web.dev/learn/accessibility

@topic a11y-landmarks-headings
title: Landmarki i hierarchia nagłówków
level: mid
tags: landmarks, headings, h1, nawigacja, skip link
summary: Landmarki (header, nav, main, footer) i logiczna hierarchia nagłówków h1-h6 to "spis treści" strony dla czytników ekranu. Użytkownicy nawigują po nich skrótami.

::: body
- Użytkownicy czytników ekranu często **skaczą po nagłówkach** i **landmarkach**, zamiast czytać stronę od początku.
- Jeden `<main>` na stronę. Kilka `<nav>` rozróżniaj przez `aria-label` ("Główna", "Stopka").
- Nagłówki odzwierciedlają strukturę treści, nie rozmiar czcionki: `h1` → `h2` → `h3`, bez przeskakiwania poziomów. Wygląd zmieniasz w CSS.
- **Skip link** "Przejdź do treści" jako pierwszy fokusowalny element pozwala pominąć nawigację.

::: code html
<a class="skip-link" href="#main">Przejdź do treści</a>
<header>
  <nav aria-label="Główna">...</nav>
</header>
<main id="main">
  <h1>Wakacje w Grecji</h1>
  <section aria-labelledby="crete">
    <h2 id="crete">Kreta</h2>
    <h3>Hotele przy plaży</h3>
  </section>
</main>
<footer><nav aria-label="Stopka">...</nav></footer>

::: qa
Q: Po co landmarki i poprawne nagłówki?
A: Tworzą strukturę, po której użytkownicy technologii asystujących nawigują skrótami (lista nagłówków, skok do main). Poprawna hierarchia pozwala zrozumieć stronę bez czytania całości, a przy okazji pomaga SEO.

::: sources
- W3C WAI-ARIA APG: Landmark Regions | https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/
- W3C WAI: Headings tutorial | https://www.w3.org/WAI/tutorials/page-structure/headings/

@topic a11y-aria
title: ARIA i pierwsza zasada ARIA
level: mid
tags: ARIA, role, aria-label, aria-expanded, live regions
summary: ARIA to atrybuty uzupełniające drzewo dostępności o role, nazwy i stany tam, gdzie HTML nie wystarcza. Pierwsza zasada: jeśli możesz użyć natywnego elementu HTML, nie używaj ARIA.

::: body
ARIA **zmienia tylko to, co ogłasza czytnik ekranu**. Nie dodaje zachowania: `role="button"` nie sprawi, że `div` stanie się fokusowalny ani zareaguje na Enter.

Trzy grupy atrybutów:

- **Role**: `role="dialog"`, `tablist`, `tab`, `tabpanel`, `alert`, `status`.
- **Właściwości (properties)**: `aria-label`, `aria-labelledby`, `aria-describedby`, `aria-controls`.
- **Stany (states)**: `aria-expanded`, `aria-pressed`, `aria-selected`, `aria-checked`, `aria-disabled`, `aria-invalid`, `aria-current="page"`.

Przydatne:

- **Live regions**: `aria-live="polite"` lub `role="status"` ogłasza dynamiczne zmiany (np. "Znaleziono 24 oferty"). `role="alert"` dla pilnych komunikatów.
- `aria-hidden="true"`: ukrywa dekoracje przed czytnikiem (np. ikony obok tekstu). Nigdy na elementach fokusowalnych.

"No ARIA is better than bad ARIA": błędne ARIA częściej szkodzi, niż pomaga. Złożone widgety (tabs, combobox, menu) buduj według wzorców **WAI-ARIA Authoring Practices** lub gotowych bibliotek (Radix UI, React Aria, Headless UI).

::: code html
<!-- Disclosure button -->
<button aria-expanded="false" aria-controls="filters">Filtry</button>
<div id="filters" hidden>...</div>

<!-- Icon-only button needs an accessible name -->
<button aria-label="Dodaj do ulubionych">
  <svg aria-hidden="true">...</svg>
</button>

<!-- Announce dynamic results -->
<p role="status">Znaleziono 24 oferty</p>

::: qa
Q: Jaka jest pierwsza zasada ARIA?
A: Jeśli istnieje natywny element lub atrybut HTML z potrzebną semantyką i zachowaniem, użyj go zamiast dodawać role i atrybuty ARIA do innego elementu. Natywne elementy mają wbudowaną obsługę klawiatury, focusu i stanów.
Q: Czy role="button" wystarczy, żeby div był dostępnym przyciskiem?
A: Nie. ARIA zmienia tylko semantykę dla technologii asystujących. Trzeba dodać `tabindex="0"`, obsługę Enter i Spacji, style focusu, stan disabled. Prościej i pewniej użyć `<button>`.
Q: Do czego służy aria-live?
A: Oznacza region, którego zmiany czytnik ekranu ogłasza automatycznie, bez przenoszenia focusu. `polite` czeka na przerwę, `assertive` przerywa. Typowo: wyniki wyszukiwania, komunikaty formularza, powiadomienia.

::: sources
- MDN: ARIA | https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA
- W3C: Using ARIA (first rule of ARIA) | https://www.w3.org/TR/using-aria/#rule1
- W3C: WAI-ARIA Authoring Practices Guide | https://www.w3.org/WAI/ARIA/apg/

@topic a11y-accessible-name
title: Accessible name: label, alt, aria-label
level: mid
tags: label, alt, accessible name, formularze
summary: Każdy interaktywny element i ważny obraz potrzebuje dostępnej nazwy, którą czytnik ekranu ogłosi. Źródła: treść elementu, label, alt, aria-labelledby, aria-label.

::: body
Kolejność ustalania nazwy (w uproszczeniu): `aria-labelledby` → `aria-label` → natywne źródło (`<label>`, `alt`, treść tekstowa przycisku lub linku, `<caption>`, `<legend>`) → `title` (ostateczność).

- **Inputy**: zawsze `<label for="id">` lub input wewnątrz `<label>`. Placeholder **nie zastępuje** labela (znika po wpisaniu, słaby kontrast).
- **Obrazy**: `alt` opisuje treść lub funkcję obrazu. Obraz dekoracyjny: `alt=""` (pusty, ale obecny).
- **Linki**: tekst mówi, dokąd prowadzi. "Kliknij tutaj" i "Więcej" poza kontekstem nic nie znaczą.
- **Błędy formularza**: powiąż komunikat przez `aria-describedby` i ustaw `aria-invalid="true"`.

::: code html
<label for="email">E-mail</label>
<input id="email" type="email" autocomplete="email"
       aria-invalid="true" aria-describedby="email-error" />
<p id="email-error">Podaj poprawny adres e-mail.</p>

<img src="hotel.jpg" alt="Hotel Blue Sea z basenem przy plaży" />
<img src="wave.svg" alt="" />  <!-- decorative -->

<a href="/oferty/kreta">Zobacz oferty na Krecie</a>

::: qa
Q: Czy placeholder może zastąpić label?
A: Nie. Placeholder znika po rozpoczęciu pisania, zwykle ma za niski kontrast i nie zawsze jest ogłaszany jako nazwa pola. Pole potrzebuje widocznego `<label>` powiązanego przez `for`/`id`.
Q: Jak pisać tekst alternatywny?
A: Opisać to, co obraz przekazuje w kontekście strony (treść lub funkcję), zwięźle. Obrazy czysto dekoracyjne dostają `alt=""`, żeby czytnik je pominął. Ikona w przycisku bez tekstu wymaga nazwy na przycisku (`aria-label`).

::: sources
- MDN Glossary: Accessible name | https://developer.mozilla.org/en-US/docs/Glossary/Accessible_name
- W3C WAI: Images tutorial (alt decision tree) | https://www.w3.org/WAI/tutorials/images/decision-tree/
- W3C WAI: Forms tutorial | https://www.w3.org/WAI/tutorials/forms/

@topic a11y-keyboard-focus
title: Klawiatura i focus management
level: senior
tags: focus, tabindex, keyboard, dialog, focus trap, focus-visible
summary: Wszystko, co działa myszą, musi działać z klawiatury. W aplikacjach SPA to Ty zarządzasz focusem: w modalach, po zmianie trasy i po usunięciu elementów.

::: body
**Podstawy:**

- Kolejność Tab wynika z kolejności w DOM. Nie przestawiaj jej `tabindex` > 0.
- `tabindex="0"`: element dodany do naturalnej kolejności. `tabindex="-1"`: fokusowalny tylko programowo (`el.focus()`).
- Widoczny focus: nigdy `outline: none` bez zamiennika. `:focus-visible` pokazuje obwódkę przy nawigacji klawiaturą, nie przy kliknięciu.

**Focus management w SPA:**

- **Modal**: po otwarciu focus do środka (pierwszy element lub nagłówek), **focus trap** (Tab nie wychodzi poza modal), Escape zamyka, po zamknięciu focus **wraca** na element, który otworzył modal. Natywny `<dialog>` z `showModal()` daje większość tego za darmo (także `inert` dla tła).
- **Zmiana trasy**: przenieś focus na `h1` nowej strony lub ogłoś zmianę; inaczej czytnik zostaje "w próżni".
- **Usunięcie elementu z focusem**: przenieś focus na sensowny sąsiedni element.
- **Roving tabindex**: w złożonych widgetach (tabs, menu, grid) jeden element grupy ma `tabindex="0"`, reszta `-1`, a strzałki przenoszą focus.
- Atrybut `inert` wyłącza interakcję i focus w całym poddrzewie.

::: code tsx
function BookingDialog({ open, onClose }: { open: boolean; onClose: () => void }) {
  const ref = useRef<HTMLDialogElement>(null);
  useEffect(() => {
    const dialog = ref.current;
    if (!dialog) return;
    if (open && !dialog.open) dialog.showModal(); // focus moves inside, background becomes inert
    if (!open && dialog.open) dialog.close();     // focus returns to the opener
  }, [open]);
  return (
    <dialog ref={ref} onClose={onClose} aria-labelledby="booking-title">
      <h2 id="booking-title">Potwierdź rezerwację</h2>
      <button onClick={onClose}>Zamknij</button>
    </dialog>
  );
}

::: qa
Q: Jak powinien działać dostępny modal?
A: Po otwarciu focus trafia do środka, Tab krąży tylko po elementach modala (focus trap), tło jest nieaktywne (`inert`), Escape zamyka, a po zamknięciu focus wraca do elementu, który otworzył modal. Modal ma rolę dialog i nazwę (`aria-labelledby`). Natywny `<dialog>` z `showModal()` realizuje większość z tego automatycznie.
Q: Co to jest :focus-visible?
A: Pseudoklasa pasująca, gdy przeglądarka uzna, że focus powinien być widoczny (zwykle przy nawigacji klawiaturą). Pozwala ukryć obwódkę po kliknięciu myszą, bez odbierania jej użytkownikom klawiatury.
Q: Co robisz z focusem po zmianie trasy w SPA?
A: Przenoszę go na główny nagłówek nowej strony (z `tabindex="-1"`) lub na kontener treści i aktualizuję `document.title`, ewentualnie ogłaszam zmianę przez live region. Bez tego użytkownik czytnika nie wie, że strona się zmieniła.

::: sources
- MDN: Keyboard-navigable JavaScript widgets | https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Keyboard-navigable_JavaScript_widgets
- MDN: The dialog element | https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog
- W3C APG: Dialog (Modal) Pattern | https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/
- MDN: :focus-visible | https://developer.mozilla.org/en-US/docs/Web/CSS/:focus-visible

@topic a11y-wcag
title: WCAG, POUR i European Accessibility Act
level: mid
tags: WCAG, POUR, kontrast, EAA, prawo
summary: WCAG to standard dostępności oparty na czterech zasadach POUR. Poziom AA to typowy wymóg prawny, a od czerwca 2025 European Accessibility Act obejmuje m.in. e-commerce w UE.

::: body
**POUR:**

- **Perceivable (postrzegalność)**: alternatywy tekstowe, napisy do wideo, kontrast, treść niezależna od koloru.
- **Operable (funkcjonalność)**: obsługa z klawiatury, wystarczający czas, brak migających treści, widoczny focus, cele dotykowe odpowiedniej wielkości.
- **Understandable (zrozumiałość)**: czytelny język, przewidywalne zachowanie, pomoc przy błędach formularza.
- **Robust (solidność)**: poprawny kod działający z technologiami asystującymi.

Poziomy: **A**, **AA** (standard wymagany prawnie), **AAA**. Aktualna wersja: **WCAG 2.2** (m.in. nowe kryteria dla focusu niezasłoniętego, rozmiaru celu, uwierzytelniania bez testów pamięci).

Konkretne progi AA: kontrast tekstu **4,5:1** (duży tekst 3:1), elementów UI i ikon **3:1**, powiększenie do 200% bez utraty treści, reflow przy szerokości 320 px.

**European Accessibility Act (EAA)** stosowany od 28 czerwca 2025: wymogi dostępności dla m.in. sklepów internetowych, bankowości, transportu i usług rezerwacyjnych w UE (w Polsce ustawa o zapewnianiu spełniania wymagań dostępności). Dla firm e-commerce i turystycznych to wymóg prawny, a nie "miły dodatek".

::: qa
Q: Co oznacza akronim POUR?
A: Cztery zasady WCAG: Perceivable (treść da się odebrać zmysłami), Operable (interfejs da się obsłużyć, np. klawiaturą), Understandable (treść i działanie są zrozumiałe), Robust (kod działa z różnymi technologiami asystującymi).
Q: Jaki kontrast wymaga WCAG AA?
A: 4,5:1 dla zwykłego tekstu, 3:1 dla dużego tekstu (ok. 24 px lub 18,5 px pogrubiony) oraz 3:1 dla elementów interfejsu i grafik niosących informację.
Q: Dlaczego dostępność to wymóg biznesowy?
A: Od 2025 roku EAA nakłada wymogi dostępności na e-commerce i wiele usług w UE, z karami za niezgodność. Poza prawem: szerszy rynek (ok. 1 na 5 osób ma jakąś niepełnosprawność, dochodzą seniorzy i sytuacyjne ograniczenia), lepsze SEO i UX dla wszystkich.

::: sources
- W3C: WCAG 2.2 Quick Reference | https://www.w3.org/WAI/WCAG22/quickref/
- W3C WAI: WCAG 2 Overview | https://www.w3.org/WAI/standards-guidelines/wcag/
- European Commission: European Accessibility Act | https://commission.europa.eu/strategy-and-policy/policies/justice-and-fundamental-rights/disability/union-equality-strategy-rights-persons-disabilities-2021-2030/european-accessibility-act_en

@topic a11y-testing
title: Jak testować dostępność
level: mid
tags: axe, Lighthouse, screen reader, Testing Library, testy
summary: Automaty (axe, Lighthouse) wykrywają tylko część problemów. Resztę znajdziesz testem klawiaturą, czytnikiem ekranu i przeglądem kodu.

::: body
1. **Automatyczne narzędzia**: axe DevTools, Lighthouse Accessibility, eslint-plugin-jsx-a11y, `@axe-core/playwright` w testach E2E. Wykrywają brak alt, labeli, słaby kontrast, złe ARIA. Szacunkowo około 30-40% problemów.
2. **Test klawiaturą**: przejdź całą ścieżkę (np. wyszukiwanie → oferta → rezerwacja) tylko Tab, Shift+Tab, Enter, Spacja, strzałki, Escape. Czy focus jest widoczny i logiczny? Czy nic nie "łapie" focusu?
3. **Czytnik ekranu**: VoiceOver (macOS/iOS), NVDA (Windows, darmowy), TalkBack (Android).
4. **DevTools**: panel Accessibility (drzewo dostępności, nazwy, role), emulacja wad wzroku, sprawdzanie kontrastu.
5. **Powiększenie** do 200-400% i szerokość 320 px.
6. **Testy komponentów**: Testing Library z zapytaniami `getByRole('button', { name: 'Rezerwuj' })` wymusza dostępne nazwy.

::: code ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('offer page has no detectable a11y violations', async ({ page }) => {
  await page.goto('/oferty/kreta');
  const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze();
  expect(results.violations).toEqual([]);
});

::: qa
Q: Jak testujesz dostępność w projekcie?
A: Automatycznie (eslint-plugin-jsx-a11y, axe w testach E2E, Lighthouse w CI) oraz ręcznie: przejście kluczowych ścieżek klawiaturą, test czytnikiem ekranu (NVDA, VoiceOver), powiększenie i kontrast. W testach komponentów używam zapytań po rolach i nazwach.
Q: Czy wynik 100 w Lighthouse Accessibility oznacza dostępną stronę?
A: Nie. Automaty sprawdzają tylko część kryteriów, które da się zweryfikować maszynowo. Nie ocenią sensowności tekstów alternatywnych, logiki focusu, zrozumiałości ani działania złożonych widgetów.

::: sources
- Deque: axe-core | https://github.com/dequelabs/axe-core
- Testing Library: ByRole | https://testing-library.com/docs/queries/byrole/
- Chrome DevTools: Accessibility features reference | https://developer.chrome.com/docs/devtools/accessibility/reference
