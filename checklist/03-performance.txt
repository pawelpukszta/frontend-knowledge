[largest-contentful-paint] critical
T: LCP poniżej 2,5 s
D: Największy element treści widoczny w viewporcie (zwykle zdjęcie hero lub nagłówek) renderuje się w ciągu 2,5 s na 75. percentylu wizyt. Najczęstsze przyczyny słabego LCP: wolny TTFB, późno odkryty lub lazy-loadowany obraz, blokujący CSS/JS.
W: LCP to moment, w którym użytkownik widzi, że strona ma to, czego szukał (np. zdjęcie hotelu i cenę); im później, tym większa szansa, że wróci do wyników wyszukiwania.
W: LCP jest jednym z trzech Core Web Vitals, które Google uwzględnia w sygnałach page experience; ocena liczy się na danych z prawdziwych wizyt (CrUX), nie z Lighthouse.
W: Wg raportu Deloitte "Milliseconds Make Millions" przyspieszenie strony mobilnej o 0,1 s zwiększyło konwersję w branży turystycznej o ok. 10%.
V: PageSpeed Insights (dane field z CrUX) oraz panel Performance w DevTools, który rozbija LCP na fazy: TTFB, opóźnienie i czas ładowania zasobu, opóźnienie renderowania. W produkcji zbieraj LCP z atrybucją przez bibliotekę `web-vitals`.
```js RUM: LCP z atrybucją (web-vitals v5)
import { onLCP } from 'web-vitals/attribution';

onLCP(({ name, value, rating, attribution }) => {
  const payload = {
    name,                       // "LCP"
    value: Math.round(value),   // ms
    rating,                     // "good" | "needs-improvement" | "poor"
    element: attribution.target,           // CSS selector of the LCP element
    ttfb: attribution.timeToFirstByte,
    loadDelay: attribution.resourceLoadDelay,  // high value = image discovered late
    loadDuration: attribution.resourceLoadDuration,
    renderDelay: attribution.elementRenderDelay,
    page: location.pathname,
  };
  navigator.sendBeacon('/api/vitals', JSON.stringify(payload));
});
```
X: Optymalizowanie wyniku Lighthouse z szybkiego laptopa zamiast danych field z telefonów użytkowników.
X: Obraz LCP ustawiony jako `background-image` w CSS albo wstawiany przez JS: przeglądarka odkrywa go dopiero po pobraniu stylów lub skryptu.
S: web.dev: Optimize LCP | https://web.dev/articles/optimize-lcp

[cumulative-layout-shift] high
T: CLS poniżej 0,1
D: Strona nie "skacze" podczas ładowania ani używania: obrazy i wideo mają wymiary, reklamy, banery i embedy mają zarezerwowane miejsce, a fonty nie zmieniają układu. Próg: 0,1 na 75. percentylu.
W: Przesunięcie układu w chwili kliknięcia powoduje przypadkowe akcje, np. tapnięcie w baner zamiast w "Zarezerwuj", co frustruje i podważa zaufanie do serwisu.
W: Czytający traci miejsce w tekście, gdy treść nagle zjeżdża w dół; najbardziej odczuwają to użytkownicy telefonów i czytników ekranu z powiększeniem.
W: Yahoo! JAPAN News po obniżeniu CLS o 0,2 odnotowało ok. 15% więcej odsłon na sesję (case study na web.dev).
V: PageSpeed Insights (field), ścieżka Layout shifts w DevTools Performance oraz insight o przyczynach przesunięć (layout shift culprits) w Lighthouse; w RUM `onCLS` z `web-vitals/attribution` podaje `largestShiftTarget`.
```html Źle
<img src="/img/hotel-santorini.avif" alt="Hotel na Santorini">
<div id="promo-banner"></div> <!-- banner injected later pushes content down -->
```
```css Dobrze
/* HTML: <img src="..." alt="..." width="1200" height="800"> */
img, video { max-width: 100%; height: auto; } /* keeps the aspect ratio from width/height */
.promo-banner { min-height: 96px; }         /* reserve space before the banner loads */
.ad-slot--mpu { width: 300px; aspect-ratio: 300 / 250; }
.map-embed { aspect-ratio: 16 / 9; }
```
X: Wstawianie banerów cookies, promocji lub "pobierz aplikację" nad treścią zamiast jako nakładki lub w zarezerwowanym miejscu.
X: Animowanie `top`, `height` lub `margin` zamiast `transform`.
S: web.dev: Optimize CLS | https://web.dev/articles/optimize-cls

[first-contentful-paint] high
T: FCP poniżej 1,8 s
D: Pierwszy tekst lub obraz pojawia się w ciągu 1,8 s, co daje użytkownikowi sygnał, że strona działa. FCP zależy głównie od TTFB i zasobów blokujących renderowanie (CSS, synchroniczne skrypty, fonty).
W: Biały ekran jest dla użytkownika nieodróżnialny od awarii; po kilku sekundach bez reakcji wielu wciska Wstecz, zanim cokolwiek zobaczy.
W: FCP to dolna granica LCP: dopóki nic się nie wyrenderowało, największy element też nie może się pojawić.
W: Na wolnej sieci komórkowej każdy blokujący plik w `<head>` to dodatkowy round-trip, często kilkaset milisekund.
V: Lighthouse, PageSpeed Insights (field i lab), filmstrip w WebPageTest lub panelu Performance: pierwsza klatka z treścią.
```html Kolejność w head przyspieszająca FCP
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Last minute Grecja | Example</title>
  <!-- Small critical CSS inline: header, hero, search form -->
  <style>header{height:64px}.hero{aspect-ratio:16/9;background:#e8eef5}</style>
  <link rel="preload" href="/fonts/inter-latin-ext.woff2" as="font" type="font/woff2" crossorigin>
  <link rel="stylesheet" href="/css/main.4f9a1c.css">
  <!-- Scripts never block parsing -->
  <script src="/js/app.8d21e0.js" type="module"></script>
</head>
```
X: Strona renderowana wyłącznie po stronie klienta: do czasu pobrania i wykonania bundla użytkownik widzi pusty `<div id="root">`.
S: web.dev: First Contentful Paint | https://web.dev/articles/fcp

[interaction-to-next-paint] high
T: INP poniżej 200 ms
D: Strona reaguje na kliknięcia, dotyk i klawiaturę bez opóźnień: od interakcji do następnej klatki mija maksymalnie 200 ms na 75. percentylu. Wysoki INP to niemal zawsze długie zadania JS na wątku głównym lub zbyt drogie renderowanie po interakcji.
W: INP zastąpił FID jako Core Web Vital w marcu 2024 i mierzy wszystkie interakcje w trakcie wizyty, a nie tylko pierwszą, więc ujawnia problemy w filtrach, formularzach i koszykach.
W: Brak natychmiastowej reakcji powoduje wielokrotne klikanie, np. podwójne dodanie do koszyka lub podwójne wysłanie rezerwacji.
W: Telefony ze średniej i niskiej półki mają kilkukrotnie słabsze CPU niż laptop dewelopera; zadanie trwające 50 ms lokalnie może u nich trwać 300 ms.
V: Dane field (CrUX w PageSpeed Insights, RUM z `onINP` z `web-vitals/attribution`: `interactionTarget`, `inputDelay`, `processingDuration`, `presentationDelay`); lokalnie nagranie interakcji w DevTools Performance z throttlingiem CPU 4x lub 6x.
```js Oddanie wątku głównego w długim handlerze
// Yield to the main thread so the browser can paint feedback first
function yieldToMain() {
  if (globalThis.scheduler?.yield) return scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}

filterForm.addEventListener('change', async (event) => {
  showSpinner();                 // cheap visual feedback, painted right away
  await yieldToMain();
  const offers = applyFilters(allOffers, new FormData(filterForm)); // heavy work
  await yieldToMain();
  renderOfferList(offers);
  sendAnalytics('filter_change'); // non-critical, could also go to requestIdleCallback
});
```
X: Synchroniczne wysyłanie analityki, walidacja całego formularza i ponowne renderowanie całej listy w jednym handlerze.
X: Testowanie INP tylko w Lighthouse: lab nie wykonuje interakcji, pokazuje co najwyżej TBT jako przybliżenie.
S: web.dev: Optimize INP | https://web.dev/articles/optimize-inp

[page-load-time] high
T: Czas ładowania poniżej 3 s
D: Strona jest używalna (główna treść widoczna, kluczowe elementy działają) w mniej niż 3 s na typowym telefonie i sieci komórkowej. Mierz na reprezentatywnym urządzeniu i sieci, a nie na laptopie dewelopera z szybkim Wi-Fi.
W: Wg danych Google z 2016 r. ponad połowa (53%) wizyt mobilnych jest porzucana, gdy strona ładuje się dłużej niż 3 s; szczegóły się zmieniają, ale zależność "wolniej, więcej porzuceń" jest stała.
W: Użytkownik szukający oferty porównuje kilka serwisów równolegle; wolniejsza karta przegrywa, zanim pokaże cenę.
W: "Czas ładowania" jest pojęciem mglistym; rozbij go na mierzalne metryki (TTFB, FCP, LCP) i ustal dla nich budżety.
V: WebPageTest z kilku lokalizacji na profilu mobilnym, Lighthouse z throttlingiem, RUM (Navigation Timing i Core Web Vitals) z podziałem na urządzenia i typ połączenia.
```js RUM: kluczowe momenty ładowania z Navigation Timing
addEventListener('load', () => {
  // Wait one task so loadEventEnd is filled in
  setTimeout(() => {
    const [nav] = performance.getEntriesByType('navigation');
    navigator.sendBeacon('/api/rum', JSON.stringify({
      page: location.pathname,
      ttfb: Math.round(nav.responseStart),
      domContentLoaded: Math.round(nav.domContentLoadedEventEnd),
      load: Math.round(nav.loadEventEnd),
      connection: navigator.connection?.effectiveType ?? 'unknown', // Chromium only
    }));
  }, 0);
});
```
X: Raportowanie średniej zamiast percentyli (p75, p95): średnia ukrywa najwolniejszych użytkowników.

[ttfb] medium
T: Krótki czas do pierwszego bajtu (TTFB)
D: Dobry TTFB to do 0,8 s na 75. percentylu. Pomagają CDN, cache na serwerze i brzegu sieci, SSG/ISR, szybsze zapytania do bazy, streaming i unikanie przekierowań.
W: TTFB poprzedza wszystko inne: żaden zasób ani piksel nie pojawi się wcześniej, więc wolny backend zjada budżet LCP, zanim frontend ma szansę zadziałać.
W: Każde przekierowanie (np. `http` na `https`, potem na `www`, potem na wersję językową) to osobny round-trip, na sieci mobilnej często 100-300 ms.
W: Strony generowane dla każdego zapytania od zera (bez cache) przy kampanii lub wyprzedaży last minute obciążają bazę i TTFB rośnie właśnie wtedy, gdy ruch jest najcenniejszy.
V: Zakładka Timing żądania dokumentu w Network ("Waiting for server response"), PageSpeed Insights (field), nagłówek `Server-Timing` widoczny w DevTools.
```http Odpowiedź z cache na CDN i pomiarem czasu serwera
HTTP/2 200
content-type: text/html; charset=utf-8
cache-control: public, max-age=0, s-maxage=300, stale-while-revalidate=3600
server-timing: db;dur=38;desc="offers query", render;dur=22, cdn-cache;desc=HIT
age: 41
```
X: Mierzenie TTFB tylko z serwera w tym samym regionie co aplikacja; użytkownik z Polski łączący się z backendem w USA ma zupełnie inny wynik.
S: web.dev: Optimize TTFB | https://web.dev/articles/optimize-ttfb

[browser-required] medium
T: Audyty w prawdziwej przeglądarce
D: Metryki takie jak LCP, CLS i INP wymagają wykonania JS i renderowania, więc narzędzia analizujące sam HTML ich nie zmierzą. Testuj w prawdziwej przeglądarce z throttlingiem CPU i sieci, zaczynając od widoku mobilnego.
W: Aplikacje React, Next.js czy Vue dociągają treść i układ w JS; statyczna analiza HTML nie zobaczy obrazu LCP, przesunięć układu ani długich zadań.
W: Większość ruchu w e-commerce i turystyce pochodzi z telefonów, a Google ocenia strony głównie na podstawie wersji mobilnej (mobile-first indexing).
W: Laptop dewelopera bez throttlingu ukrywa problemy, które użytkownik z tańszym telefonem odczuwa jako kilkusekundowe opóźnienia.
V: Lighthouse (domyślnie emuluje telefon z throttlingiem), PageSpeed Insights, panel Performance w DevTools z ustawieniem CPU 4x/6x i sieci "Slow 4G".

@cl-group Waga strony i zasoby
sources: web.dev: Performance budgets 101 | https://web.dev/articles/performance-budgets-101

[page-weight] high
T: Waga strony poniżej 1500 KB
D: Łączny transfer przy pierwszym wejściu (HTML, CSS, JS, obrazy, fonty) maksymalnie 1500 KB, cel poniżej 500 KB dla kluczowych stron. Ustal budżet i pilnuj go automatycznie.
W: Każdy kilobajt kosztuje czas na wolnych sieciach; na 4G z dużym opóźnieniem lub w zasięgu jednej kreski różnica 1 MB to kilka sekund.
W: Użytkownik płaci za transfer: na roamingu poza UE (np. Egipt, Turcja, Tunezja) 1 MB potrafi kosztować kilka złotych, a to typowa sytuacja klienta biura podróży sprawdzającego rezerwację na miejscu.
W: Bez budżetu waga rośnie niezauważalnie z każdą funkcją; mediana wagi strony mobilnej w HTTP Archive przekracza już 2 MB.
V: Network z wyłączonym cache, posortowany po rozmiarze (kolumna Transferred), Lighthouse (łączny rozmiar sieci), budżet sprawdzany w CI.
```ts Test budżetu wagi w Playwright
import { test, expect } from '@playwright/test';

test('offer page stays under the 1500 KB budget', async ({ page }) => {
  await page.goto('/wakacje/grecja/hotel-santorini-view', { waitUntil: 'networkidle' });
  const bytes = await page.evaluate(() =>
    performance.getEntriesByType('resource')
      .concat(performance.getEntriesByType('navigation'))
      .reduce((sum, e) => sum + (e as PerformanceResourceTiming).transferSize, 0),
  );
  console.log(`Transferred: ${Math.round(bytes / 1024)} KB`);
  expect(bytes).toBeLessThan(1500 * 1024);
});
```
X: Budżet liczony tylko dla JS, a pominięcie obrazów i fontów, które zwykle stanowią większość wagi.
X: `transferSize` równe 0 dla zasobów z innych domen bez nagłówka `Timing-Allow-Origin`; budżet trzeba wtedy liczyć np. w Lighthouse lub WebPageTest.

[http-requests] high
T: Mało zapytań HTTP
D: Na starcie orientacyjnie poniżej 50 zapytań. Usuń zbędne skrypty i style, łącz drobne ikony w sprite SVG, nie ładuj zasobów dla niewidocznych elementów. HTTP/2 i HTTP/3 łagodzą, ale nie usuwają kosztu wielu zapytań.
W: Każde zapytanie to nagłówki, priorytetyzacja, praca na wątku głównym i potencjalnie nowe połączenie do innej domeny (DNS, TCP, TLS).
W: Duża liczba zapytań zwykle oznacza dużo skryptów firm trzecich, a te dokładają kolejne zapytania kaskadowo (tag ładuje tag).
W: Przeglądarka ma ograniczoną przepustowość na starcie; drobne zapytania konkurują z obrazem LCP i krytycznym CSS.
V: Licznik zapytań na dole zakładki Network (z wyłączonym cache) oraz grupowanie po domenie w WebPageTest.
```html Sprite SVG zamiast osobnych plików ikon
<!-- One inline sprite instead of 20 separate icon requests -->
<svg width="0" height="0" style="position:absolute" aria-hidden="true">
  <symbol id="icon-pool" viewBox="0 0 24 24"><path d="M2 18c2 0 2-1 4-1s2 1 4 1 2-1 4-1 2 1 4 1 2-1 4-1"/></symbol>
  <symbol id="icon-wifi" viewBox="0 0 24 24"><path d="M2 9a15 15 0 0 1 20 0M5 13a10 10 0 0 1 14 0M9 17a4 4 0 0 1 6 0"/></symbol>
</svg>

<ul class="amenities">
  <li><svg class="icon" aria-hidden="true"><use href="#icon-pool"></use></svg> Basen</li>
  <li><svg class="icon" aria-hidden="true"><use href="#icon-wifi"></use></svg> Wi-Fi</li>
</ul>
```
X: Sklejanie wszystkiego w jeden ogromny bundle "żeby było mniej zapytań": przy HTTP/2 lepiej działa kilka sensownie podzielonych plików, które cache'ują się niezależnie.

[compression] high
T: Kompresja zasobów tekstowych
D: HTML, CSS, JS, JSON, SVG i fonty inne niż WOFF2 są wysyłane skompresowane: Brotli (lub zstd) z gzip jako zapasem. Kompresja zmniejsza transfer tekstu zwykle o 70-80%.
W: Bundle 600 KB po kompresji to ok. 150 KB; różnica ma bezpośredni wpływ na FCP, LCP i koszt transferu u użytkownika.
W: Brotli daje zwykle kilkanaście procent mniejsze pliki niż gzip; zasoby statyczne warto kompresować z najwyższym poziomem już przy buildzie, a dynamiczny HTML niższym, szybszym poziomem.
W: Nie kompresuj ponownie formatów już skompresowanych (JPEG, AVIF, WebP, WOFF2, MP4): to strata CPU bez zysku.
V: Kolumna lub nagłówek `Content-Encoding` w Network (włącz "Big request rows", by widzieć rozmiar przed i po kompresji); `curl` z nagłówkiem `Accept-Encoding`.
```bash Sprawdzenie kompresji z linii poleceń
# Expect "content-encoding: br" (or zstd/gzip) and "vary: Accept-Encoding"
curl -sI -H 'Accept-Encoding: br, gzip' https://example.pl/assets/app.3f2a9c.js \
  | grep -iE 'content-encoding|content-length|vary'

# Compare raw vs compressed size of a build artifact
ls -lh dist/assets/app.3f2a9c.js
brotli -q 11 -c dist/assets/app.3f2a9c.js | wc -c
```
X: Kompresja włączona tylko dla HTML, a API zwracające duże JSON-y z listą ofert idą bez kompresji.
S: web.dev: Reduce the size of text resources | https://web.dev/articles/reduce-network-payloads-using-text-compression

[video-optimization] high
T: Zoptymalizowane wideo
D: Wideo jest skompresowane, w nowoczesnych kodekach (AV1, VP9, z H.264 jako zapasem), w rozdzielczości dopasowanej do ekranu, z plakatem i `preload="none"` lub `metadata` dla wideo, które nie startuje od razu.
W: Kilkunastosekundowy film w tle hero potrafi ważyć więcej niż cała reszta strony; na telefonie z limitem danych to realny koszt dla użytkownika.
W: AV1 przy tej samej jakości jest zwykle wyraźnie mniejszy niż H.264, a przeglądarki bez wsparcia po prostu wybiorą kolejne `<source>`.
W: Plakat z wymiarami zapobiega przesunięciom układu i daje treść do wyświetlenia, zanim wideo się załaduje (a plakat może być elementem LCP).
V: Rozmiar plików wideo w Network (filtr Media), sprawdzenie, czy wideo poniżej zgięcia nie pobiera się przy starcie strony.
```html
<video controls preload="none" width="1280" height="720"
       poster="/video/hotel-tour-poster.avif">
  <source src="/video/hotel-tour-720p.av1.mp4" type='video/mp4; codecs="av01.0.05M.08"'>
  <source src="/video/hotel-tour-720p.vp9.webm" type="video/webm; codecs=vp9">
  <source src="/video/hotel-tour-720p.h264.mp4" type="video/mp4">
  <track kind="captions" src="/video/hotel-tour.pl.vtt" srclang="pl" label="Polski">
</video>
```
```bash Kodowanie AV1 i H.264 z ffmpeg
ffmpeg -i tour.mov -vf scale=-2:720 -c:v libsvtav1 -crf 35 -preset 6 -an hotel-tour-720p.av1.mp4
ffmpeg -i tour.mov -vf scale=-2:720 -c:v libx264 -crf 24 -preset slow -an -movflags +faststart hotel-tour-720p.h264.mp4
```
X: Wysyłanie pliku 4K do wszystkich urządzeń, także telefonów o szerokości 390 px.
X: Dłuższe filmy hostowane jako jeden plik MP4 zamiast streamingu adaptacyjnego (HLS/DASH) lub zewnętrznej platformy wideo.

[css-file-size] medium
T: Mały rozmiar CSS
D: CSS blokuje renderowanie, więc każdy kilobajt opóźnia FCP. Cel: do ok. 50 KB po kompresji dla stylów potrzebnych na starcie; minifikacja, usuwanie nieużywanych reguł, podział na trasy i media.
W: Przeglądarka nie wyrenderuje niczego, dopóki nie pobierze i nie przetworzy całego CSS z `<head>`, nawet reguł dla stron, których użytkownik nie odwiedzi.

import { registerRoute } from 'workbox-routing';
import { CacheFirst, StaleWhileRevalidate, NetworkFirst } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';

    plugins: [new ExpirationPlugin({ maxEntries: 200, maxAgeSeconds: 30 * 24 * 3600 })] }));

const CACHE = 'offline-v3';

self.addEventListener('install', (event) => {

      return cache.match(OFFLINE_URL);

});

import { lazy, Suspense, useEffect, useRef, useState } from 'react';

const HotelMap = lazy(() => import('./HotelMap'));

export function LazyHotelMap({ lat, lng }: { lat: number; lng: number }) {
  const ref = useRef<HTMLDivElement>(null);
  const [visible, setVisible] = useState(false);

  useEffect(() => {
    const io = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) { setVisible(true); io.disconnect(); }

    return () => io.disconnect();

    <div ref={ref} style={{ minHeight: 400 }}>
      {visible && <Suspense fallback={<MapSkeleton />}><HotelMap lat={lat} lng={lng} /></Suspense>}
    </div>
  );
}

[consent-mode] high
T: Google Consent Mode v2
D: Tagi Google dostosowują zachowanie do zgód użytkownika (`ad_storage`, `analytics_storage`, `ad_user_data`, `ad_personalization`). Domyślny stan zgód ustawiasz przed załadowaniem tagów, a po decyzji w banerze aktualizujesz go. Google wymaga tych sygnałów dla ruchu z EOG, aby korzystać z pomiaru konwersji, personalizacji reklam i remarketingu.
W: Od marca 2024 Google wymaga sygnałów `ad_user_data` i `ad_personalization` dla użytkowników z EOG; bez nich kampanie tracą remarketing i część danych o konwersjach.
W: Ustawienie stanu domyślnego na `denied` przed ładowaniem tagów to warunek zgodności z RODO i dyrektywą ePrivacy: żadne cookies reklamowe nie mogą powstać przed zgodą.
W: Tryb zaawansowany (tagi ładują się, ale wysyłają pingi bez cookies) pozwala modelować konwersje dla osób bez zgody; tryb podstawowy w ogóle nie ładuje tagów do czasu zgody.
V: Tag Assistant: stan zgód przed i po akceptacji banera; w Network parametr `gcs`/`gcd` w zapytaniach do Google; Application → Cookies: brak `_ga` i cookies reklamowych przed zgodą.

    ad_user_data: 'denied',
    ad_personalization: 'denied',
    analytics_storage: 'denied',
    wait_for_update: 500, // ms to wait for the consent banner (CMP)
  });
  dataLayer.push({ 'gtm.start': Date.now(), event: 'gtm.js' }); // part of the standard GTM snippet
</script>

<script>
  // Called by the consent banner after the user's choice
  function onConsentSaved({ analytics, marketing }) {
    gtag('consent', 'update', {
      analytics_storage: analytics ? 'granted' : 'denied',
      ad_storage: marketing ? 'granted' : 'denied',
