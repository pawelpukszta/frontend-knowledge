@cl-group Strategia testów
sources: Kent C. Dodds: The Testing Trophy | https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications

[unit-tests] high
T: Testy jednostkowe
D: Logika domenowa, funkcje pomocnicze, hooki i reducery mają szybkie, izolowane testy (Vitest, Jest) uruchamiane lokalnie w trybie watch i w CI przy każdym pushu.
W: Błąd w wyliczaniu ceny, rabatu czy liczby nocy kosztuje realne pieniądze i zaufanie klientów; test jednostkowy łapie go w milisekundach, zanim kod trafi do code review.
W: Testy dokumentują przypadki brzegowe (zmiana czasu, rok przestępny, dziecko za pół ceny) lepiej niż komentarz i chronią logikę przy refaktoryzacji.
W: To najtańsze i najszybsze testy: tysiące przypadków w kilka sekund, więc programiści naprawdę je uruchamiają.
V: `npx vitest run` lokalnie i jako wymagany krok CI; czerwony wynik blokuje merge (branch protection).
```ts src/pricing/calculate-total.test.ts
import { describe, expect, test } from 'vitest';
import { calculateTotal } from './calculate-total';

describe('calculateTotal', () => {
  test.each([
    // adults, children, nights, expected total in PLN (350 PLN per person per night)
    [2, 0, 7, 4900],
    [2, 1, 7, 6125], // a child pays 50%
    [1, 0, 0, 0],    // zero nights means no charge
  ])('%i adults, %i children, %i nights -> %i PLN', (adults, children, nights, expected) => {
    expect(calculateTotal({ adults, children, nights, pricePerNight: 350 })).toBe(expected);
  });

  test('rejects a negative number of guests', () => {
    expect(() => calculateTotal({ adults: -1, children: 0, nights: 3, pricePerNight: 350 })).toThrow(RangeError);
  });
});
```
X: Testowanie szczegółów implementacji (prywatnych funkcji, liczby wywołań `setState`) zamiast wyniku.
X: Testy zależne od bieżącej daty lub strefy czasowej maszyny zamiast `vi.setSystemTime` i jawnej strefy.

[integration-testing] high
T: Testy integracyjne kluczowych procesów
D: Testy wielu jednostek razem: komponent renderowany z prawdziwymi hookami, routerem i stanem, a sieć zastąpiona na granicy przez MSW; po stronie serwera trasa API z prawdziwą (testową) bazą danych. Na froncie dają najlepszy stosunek pewności do kosztu.
W: Większość błędów powstaje na stykach: komponent dostaje inny kształt danych, cache TanStack Query nie unieważnia się po mutacji, formularz nie obsługuje odpowiedzi 422.
W: Testy pisane z perspektywy użytkownika (role, etykiety, teksty) przeżywają refaktoryzację; zamiana Redux na Zustand nie wymaga ich przepisywania.
W: Są wielokrotnie szybsze i stabilniejsze niż E2E, więc mogą pokryć także stany ładowania, pustego wyniku i błędu API, które w E2E trudno wywołać.
V: Każda kluczowa ścieżka (wyszukiwanie, filtrowanie, koszyk, formularz rezerwacji) ma testy integracyjne dla sukcesu, pustego wyniku i błędu; uruchamiane w CI razem z testami jednostkowymi.
```tsx src/features/search/search-page.test.tsx
import { afterAll, afterEach, beforeAll, expect, test } from 'vitest';
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';
import { screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { renderWithProviders } from '@/test/render-with-providers'; // QueryClient, router, i18n
import { SearchPage } from './search-page';

const server = setupServer(
  http.get('/api/offers', ({ request }) => {
    const destination = new URL(request.url).searchParams.get('destination');
    return HttpResponse.json([{ id: '1', title: `Hotel Lindos, ${destination}`, price: 3499 }]);
  }),
);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test('shows offers for the chosen destination', async () => {
  const user = userEvent.setup();
  renderWithProviders(<SearchPage />);
  await user.type(screen.getByRole('combobox', { name: 'Dokąd jedziesz?' }), 'Rodos');
  await user.click(screen.getByRole('button', { name: 'Szukaj' }));
  expect(await screen.findByRole('heading', { name: /Hotel Lindos, Rodos/ })).toBeInTheDocument();
});
```
X: Test integracyjny, który mockuje wszystkie moduły poza testowanym komponentem; to w praktyce test jednostkowy z gorszą czytelnością.

[e2e-testing] high
T: Testy end-to-end
D: Playwright (lub Cypress) sprawdza krytyczne ścieżki użytkownika (wyszukiwanie, rezerwacja, płatność) w prawdziwej przeglądarce, na środowisku zbliżonym do produkcji, w CI przed każdym wdrożeniem.
W: Tylko E2E sprawdza całość naraz: routing, SSR i hydrację, cookies, przekierowania oraz integrację z bramką płatności w trybie testowym.
W: Awaria ścieżki rezerwacji to bezpośrednio utracony przychód; kilkanaście dobrze dobranych scenariuszy daje wiarygodny sygnał "można wdrażać".
W: E2E są wolne i podatne na niestabilność, dlatego warto mieć ich niewiele, na najważniejszych ścieżkach, z lokatorami opartymi na rolach i bez sztywnych `waitForTimeout`.
V: Raport HTML Playwright i trace z nieudanych testów jako artefakty pipeline'u; wdrożenie wymaga zielonego zestawu E2E.
```ts e2e/booking.spec.ts
import { test, expect } from '@playwright/test';

test('guest can book an offer and reach the payment step', async ({ page }) => {
  await page.goto('/wakacje/grecja');
  await page.getByRole('link', { name: /Hotel Lindos Bay/ }).click();

  await page.getByLabel('Data wyjazdu').fill('2026-07-15');
  await page.getByRole('button', { name: 'Rezerwuj' }).click();

  await page.getByLabel('Imię i nazwisko').fill('Anna Nowak');
  await page.getByLabel('E-mail').fill('anna.nowak@example.com');
  await page.getByRole('button', { name: 'Przejdź do płatności' }).click();

  // Web-first assertions retry automatically, no manual sleeps needed
  await expect(page).toHaveURL(/\/platnosc/);
  await expect(page.getByRole('heading', { name: 'Płatność' })).toBeVisible();
});
```
X: Lokatory CSS typu `.btn-primary > span:nth-child(2)`, które psują się przy każdej zmianie stylów.
X: Testy zależne od siebie nawzajem lub od danych produkcyjnych; każdy test powinien sam przygotować swoje dane.

[contract-testing] medium
T: Testy kontraktowe API
D: Kontrakty konsumenckie (Pact) lub wspólny schemat OpenAPI z generowanymi typami wykrywają niezgodność frontu i backendu przed wdrożeniem, a nie na produkcji.
W: Zmiana nazwy pola `price` na `totalPrice` przechodzi testy backendu i testy frontu z mockami, a psuje stronę u użytkowników; kontrakt wyłapuje to w CI.
W: Front i backend mogą wdrażać się niezależnie: `can-i-deploy` w Pact Broker sprawdza, czy konkretne wersje obu stron są zgodne.
W: Mocki (np. handlery MSW) budowane z tego samego kontraktu przestają rozjeżdżać się z rzeczywistym API.
V: Testy konsumenta publikują kontrakt do brokera, a pipeline dostawcy go weryfikuje; przy OpenAPI: generowanie typów (`npx openapi-typescript`) w CI i `tsc --noEmit` bez błędów.
```ts src/api/offers.pact.test.ts
import path from 'node:path';
import { expect, test } from 'vitest';
import { Pact, MatchersV3, SpecificationVersion } from '@pact-foundation/pact';
import { fetchOffer } from './offers-client';

const { like, decimal, string } = MatchersV3;
const provider = new Pact({
  consumer: 'travel-web',
  provider: 'offers-api',
  dir: path.resolve(process.cwd(), 'pacts'),
  spec: SpecificationVersion.SPECIFICATION_VERSION_V4,
});

test('fetches a single offer', async () => {
  await provider
    .addInteraction()
    .given('offer 123 exists')
    .uponReceiving('a request for offer 123')
    .withRequest('GET', '/api/offers/123')
    .willRespondWith(200, (builder) => {
      builder.jsonBody({ id: string('123'), title: like('Hotel Lindos'), price: decimal(3499.99) });
    })
    .executeTest(async (mockServer) => {
      const offer = await fetchOffer('123', { baseUrl: mockServer.url });
      expect(offer.price).toBe(3499.99);
    });
});
```
X: Kontrakt opisujący całą odpowiedź API zamiast pól, których front faktycznie używa; każda zmiana po stronie backendu niepotrzebnie go łamie.
S: Pact JS: Consumer tests | https://docs.pact.io/implementation_guides/javascript/docs/consumer

[mock-best-practices] medium
T: Rozsądne mockowanie
D: Mockuj granice systemu (sieć, czas, losowość, API przeglądarki), a nie własne moduły i szczegóły implementacji. Nadmiar mocków daje testy, które przechodzą przy zepsutej aplikacji.
W: Mock własnego hooka `useOffers` sprawdza tylko, że mock zwraca to, co mu kazano; błąd w hooku i w mapowaniu danych z API pozostaje niewykryty.
W: Asercje `toHaveBeenCalledWith` na wewnętrznych funkcjach pękają przy każdej refaktoryzacji, choć zachowanie się nie zmieniło; zespół przestaje ufać testom.
W: Mockowanie na poziomie sieci (MSW) pozwala użyć tych samych handlerów w testach, Storybooku i lokalnym developmencie.
V: Code review testów: każdy `vi.mock` lub `jest.mock` własnego modułu wymaga uzasadnienia; wyszukaj w repozytorium `vi.mock('./` i `vi.mock('@/`.
```tsx Źle
// Mocks our own hook: the test passes even if useOffers or the API mapping is broken
vi.mock('./use-offers', () => ({
  useOffers: () => ({ data: [{ id: '1', title: 'Hotel Lindos' }], isLoading: false }),
}));
```
```tsx Dobrze
// Mock only the boundaries: the network (MSW) and the clock
server.use(
  http.get('/api/offers', () => HttpResponse.json([{ id: '1', title: 'Hotel Lindos', price: 3499 }])),
);
// Fake only Date, so Testing Library's async utils keep working
vi.useFakeTimers({ toFake: ['Date'] });
vi.setSystemTime(new Date('2026-06-30T22:30:00+02:00')); // last-minute deadline edge case

renderWithProviders(<OfferList />);
expect(await screen.findByText('Hotel Lindos')).toBeInTheDocument();
expect(screen.getByText('Ostatnia chwila')).toBeInTheDocument();
```
X: Pełne `vi.useFakeTimers()` razem z `findBy*`, które przez to nigdy się nie rozwiązują.
X: Brak `onUnhandledRequest: 'error'` w MSW, przez co niezamockowane zapytania przechodzą po cichu.

[test-coverage] medium
T: Progi pokrycia testami
D: Minimalne pokrycie (np. 70-80% linii dla logiki domenowej) egzekwowane w CI zapobiega cichemu spadkowi jakości. Pokrycie to wskaźnik pomocniczy, a nie cel sam w sobie.
W: Bez progu pokrycie spada niezauważenie, bo nowy kod trafia do repozytorium bez testów "tylko na chwilę".
W: Raport pokazuje nieprzetestowane gałęzie, np. obsługę odrzuconej płatności, czyli konkretne miejsca do uzupełnienia.
W: 100% pokrycia nie oznacza dobrych testów: linia wykonana bez żadnej asercji też się liczy, dlatego progi warto łączyć z testami mutacyjnymi.
V: `npx vitest run --coverage` kończy się błędem poniżej progu; raport (np. komentarz w PR) pokazuje pokrycie zmienionych plików.
```ts vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    coverage: {
      provider: 'v8',
      // Without include, files never imported by tests do not lower the score
      include: ['src/**/*.{ts,tsx}'],
      exclude: ['src/**/*.stories.tsx', 'src/**/*.d.ts'],
      reporter: ['text', 'html', 'json-summary'],
      thresholds: {
        lines: 80, functions: 80, branches: 70, statements: 80,
        // Stricter gate for money-related logic
        'src/pricing/**': { lines: 95, branches: 90 },
      },
    },
  },
});
```
X: Pisanie testów bez asercji tylko po to, by podbić procent.
X: Jeden globalny próg 90% dla całego projektu, łącznie z kodem UI bez logiki; zespół zaczyna wykluczać pliki, żeby przejść CI.
S: Vitest: Coverage config | https://vitest.dev/config/coverage

[mutation-testing] medium
T: Testy mutacyjne krytycznej logiki
D: Stryker wprowadza drobne zmiany w kodzie (mutanty, np. `>` na `>=` albo usunięcie warunku) i sprawdza, czy testy je wykryją. Pokazuje, czy testy naprawdę sprawdzają zachowanie, a nie tylko wykonują linie.
W: Wysokie pokrycie bywa złudne: test, który wywołuje `calculateDiscount` bez sensownej asercji, daje 100% linii i zero ochrony; wynik mutacyjny (mutation score) to ujawnia.
W: Mutanty, które przeżyły, wskazują konkretny brakujący przypadek, np. brak testu dla granicy "rabat od 4 osób".
W: Pełny przebieg jest kosztowny (testy uruchamiane setki razy), dlatego zawęża się go do krytycznych modułów i używa trybu przyrostowego.
V: Raport HTML Strykera z mutation score dla wybranych modułów (np. wyliczania cen); próg `break` przerywa nocny job CI.
```json stryker.config.json
{
  "$schema": "./node_modules/@stryker-mutator/core/schema/stryker-schema.json",
  "testRunner": "vitest",
  "plugins": ["@stryker-mutator/vitest-runner", "@stryker-mutator/typescript-checker"],
  "checkers": ["typescript"],
  "tsconfigFile": "tsconfig.json",
  "mutate": ["src/pricing/**/*.ts", "!src/pricing/**/*.test.ts"],
  "incremental": true,
  "reporters": ["html", "clear-text", "progress"],
  "thresholds": { "high": 85, "low": 70, "break": 60 }
}
```
X: Uruchamianie Strykera na całym monorepo w każdym PR; przebieg trwa godzinami i szybko zostaje wyłączony.
S: Stryker Mutator | https://stryker-mutator.io/

[cross-browser-testing] high
T: Testy we wszystkich głównych przeglądarkach
D: Chrome, Firefox, Safari (także na iOS, gdzie w praktyce wszystkie przeglądarki używają silnika WebKit) i Edge. Playwright uruchamia te same testy w Chromium, Firefox i WebKit; prawdziwe Safari i nietypowe konfiguracje sprawdza się w chmurze urządzeń.
W: Silniki różnią się w szczegółach: obsługa nowszych API CSS i JS, pól formularzy, przewijania i fokusu; błąd widoczny tylko w Safari dotyka wszystkich użytkowników iPhone'ów.
W: Baseline (web.dev) mówi, które funkcje działają we wszystkich głównych silnikach; funkcje spoza Baseline wymagają testu i fallbacku.
W: WebKit w Playwright to nie jest dokładnie Safari, ale tanim kosztem, w każdym PR, łapie większość różnic silnika.
V: Macierz przeglądarek jako projekty Playwright w CI; przed wydaniem przegląd w prawdziwym Safari na macOS i iOS lub w BrowserStack albo Sauce Labs.
```ts playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  retries: process.env.CI ? 2 : 0,
  use: { baseURL: 'http://localhost:3000', trace: 'on-first-retry' },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
    { name: 'edge', use: { ...devices['Desktop Edge'], channel: 'msedge' } },
    // Mobile viewport, touch and user agent emulation on the real engines
    { name: 'mobile-safari', use: { ...devices['iPhone 15'] } },
    { name: 'mobile-chrome', use: { ...devices['Pixel 7'] } },
  ],
  webServer: { command: 'npm run start', url: 'http://localhost:3000', reuseExistingServer: !process.env.CI },
});
```
X: Testowanie wyłącznie w Chrome, bo "wszyscy go używają".
X: Używanie nowej funkcji CSS lub JS bez sprawdzenia jej statusu Baseline i bez `@supports` lub fallbacku.

[mobile-testing] high
T: Testy na prawdziwych urządzeniach mobilnych
D: Emulacja w DevTools nie oddaje wydajności słabszego procesora, klawiatury ekranowej, zachowania paska adresu ani Safari na iOS. Testuj na kilku realnych telefonach, w tym na starszym Androidzie ze średniej półki.
W: Tani Android ma kilkukrotnie słabszy procesor niż laptop programisty; INP i czas hydracji, które w emulacji wyglądają dobrze, na telefonie przekraczają progi Core Web Vitals.
W: Tylko na urządzeniu widać, że klawiatura zasłania przycisk "Rezerwuj", pole telefonu otwiera złą klawiaturę albo iOS powiększa stronę przy fokusie na polu z fontem mniejszym niż 16 px.
W: Ocena Core Web Vitals w Google opiera się na danych od prawdziwych użytkowników (CrUX), w dużej części mobilnych, a nie na pomiarach z laptopa.
V: Zdalne debugowanie: `chrome://inspect` dla Androida i Web Inspector w Safari dla iPhone'a; modele, których zespół nie ma, w chmurze urządzeń (BrowserStack, LambdaTest).
```bash Lokalny serwer na prawdziwym telefonie
# Android over USB: forward the phone's localhost:3000 to the dev machine
adb devices
adb reverse tcp:3000 tcp:3000
# Open http://localhost:3000 in Chrome on the phone,
# then inspect the tab from chrome://inspect on the desktop

# iPhone on the same Wi-Fi: expose the dev server on the local network
npx next dev --hostname 0.0.0.0
# Open http://<laptop-ip>:3000 in Safari and debug via the Develop menu on a Mac
```
X: Testowanie tylko na flagowym telefonie zespołu.
X: Uznanie trybu responsywnego w DevTools z throttlingiem CPU za wystarczający test mobilny.

[accessibility-testing] high
T: Automatyczne testy dostępności
D: axe-core w testach komponentów i E2E (`@axe-core/playwright`, vitest-axe lub jest-axe) oraz lint `eslint-plugin-jsx-a11y` wyłapują część błędów automatycznie. To uzupełnienie, a nie zastępstwo testów ręcznych z klawiaturą i czytnikiem ekranu.
W: Automaty wykrywają typowe błędy (brak etykiet, za niski kontrast, błędne atrybuty ARIA, brak `alt`) w każdym PR, zanim trafią na produkcję i do audytu.
W: Narzędzia wykrywają tylko część problemów WCAG; kolejności fokusu, sensu tekstów alternatywnych i działania z czytnikiem ekranu nie sprawdzą.
W: European Accessibility Act obowiązuje od 28 czerwca 2025 r.; regresja dostępności w sklepie lub systemie rezerwacji to ryzyko prawne, a nie tylko gorszy UX.
V: Krok a11y w CI (axe w Playwright na kluczowych stronach i stanach, np. z otwartym modalem); okresowo ręczny test klawiaturą oraz z NVDA lub VoiceOver.
```ts e2e/a11y.spec.ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

for (const path of ['/', '/wakacje/grecja', '/rezerwacja/123']) {
  test(`no detectable WCAG A/AA violations on ${path}`, async ({ page }) => {
    await page.goto(path);
    const results = await new AxeBuilder({ page })
      .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
      .exclude('#third-party-chat') // widget outside our control, tracked separately
      .analyze();
    expect(results.violations).toEqual([]);
  });
}
```
X: Skanowanie tylko stanu początkowego strony, bez otwartych menu, modali i komunikatów błędów walidacji.
X: Masowe wyłączanie reguł axe, żeby CI było zielone.
S: Playwright: Accessibility testing | https://playwright.dev/docs/accessibility-testing

[visual-regression] medium
T: Testy regresji wizualnej
D: Zrzuty ekranu porównywane z zatwierdzonymi wzorcami (Playwright `toHaveScreenshot`, Chromatic, Percy) wychwytują niezamierzone zmiany wyglądu, których nie zauważą testy funkcjonalne.
W: Zmiana jednego tokenu lub globalnego stylu potrafi rozjechać kilkadziesiąt ekranów; test funkcjonalny przejdzie, bo przycisk nadal istnieje, choć jest przykryty albo niewidoczny.
W: Recenzent w PR widzi różnicę obraz w obraz, zamiast domyślać się skutków zmiany w CSS.
W: Zrzuty zależą od systemu, fontów i przeglądarki, dlatego wzorce generuje się w tym samym środowisku co CI (np. w oficjalnym obrazie Dockera Playwright).
V: Raport różnic w PR (raport HTML Playwright lub Chromatic); wzorce aktualizuje się świadomie przez `npx playwright test --update-snapshots`, a zmiany obrazów przechodzą review.
```ts e2e/visual.spec.ts
import { test, expect } from '@playwright/test';

test('offer grid looks unchanged', async ({ page }) => {
  await page.goto('/wakacje/grecja');
  await expect(page).toHaveScreenshot('offers-grid.png', {
    fullPage: true,
    animations: 'disabled',
    // Hide content that changes on every run
    mask: [page.getByTestId('live-price'), page.getByTestId('promo-countdown')],
    maxDiffPixelRatio: 0.01,
  });
});
```
X: Wzorce generowane na macOS programisty, a porównywane w CI na Linuksie.
X: Automatyczne akceptowanie wszystkich różnic, bo "to pewnie antyaliasing".
S: Playwright: Visual comparisons | https://playwright.dev/docs/test-snapshots

[performance-budget] medium
T: Budżety wydajności w CI
D: Limity (rozmiar JS, LCP, CLS, liczba zapytań) sprawdzane automatycznie w każdym PR (Lighthouse CI, size-limit); przekroczenie blokuje merge.
W: Wydajność psuje się po trochu: każda biblioteka dodaje kilkadziesiąt KB i nikt nie czuje się odpowiedzialny; budżet zamienia to w jawną decyzję w PR.

```ts app/api/account/route.ts
import { auth, hasRecentLogin } from '@/lib/auth';
import { db } from '@/lib/db';
import { newsletter, crm } from '@/lib/integrations';

export async function DELETE() {
  const session = await auth();
  if (!session) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
  // Require a recent login so a stolen session cannot wipe the account
  if (!hasRecentLogin(session)) {
    return NextResponse.json({ error: 'Reauthentication required' }, { status: 403 });

    db.user.delete({ where: { id: userId } }),
  ]);

  return new NextResponse(null, { status: 204 });
}
```

```ts scripts/pseudo-locale.ts
// Accented characters reveal hard-coded strings,
// ~40% padding reveals layouts that break with longer translations
const map: Record<string, string> = { a: 'á', e: 'é', i: 'í', o: 'ö', u: 'ü', c: 'ç', n: 'ñ', s: 'š', z: 'ž' };

export function pseudo(text: string): string {
  // Keep simple placeholders like {name} untouched
  const parts = text.split(/(\{[^}]*\})/);
  const body = parts.map((p, i) => (i % 2 ? p : p.replace(/[a-z]/g, (ch) => map[ch] ?? ch))).join('');
  return `[${body}${'~'.repeat(Math.ceil(text.length * 0.4))}]`;
}

pseudo('Book now'); // "[Böök ñöw~~~~]"
```

[hreflang] medium
T: Tagi hreflang dla wersji językowych
D: `<link rel="alternate" hreflang="pl-PL" href="...">` dla każdej wersji językowej, z wzajemnymi odwołaniami, odwołaniem do samej siebie i `x-default`, wskazuje wyszukiwarkom właściwą wersję dla użytkownika.
W: Bez hreflang Google może pokazać polskiemu użytkownikowi wersję angielską albo potraktować bardzo podobne wersje (np. `de-DE` i `de-AT`) jak duplikaty.
W: Odwołania muszą być dwustronne: jeśli strona A wskazuje B, a B nie wskazuje A, adnotacje mogą zostać zignorowane.
W: `x-default` wskazuje stronę dla użytkowników spoza obsługiwanych języków, np. stronę wyboru języka lub wersję angielską.
W: Kody to ISO 639-1 dla języka i opcjonalnie ISO 3166-1 alpha-2 dla regionu (`en-GB`, a nie `en-UK`); błędny kod jest pomijany.
V: Crawler z raportem hreflang (np. Screaming Frog): brak błędów odwołań zwrotnych, kodów i adresów nieindeksowalnych; canonical każdej wersji wskazuje na nią samą.
```html

<link rel="alternate" hreflang="de-DE" href="https://example.com/de/urlaub/griechenland" />
<link rel="alternate" hreflang="en-GB" href="https://example.com/en/holidays/greece" />
<link rel="alternate" hreflang="x-default" href="https://example.com/en/holidays/greece" />
```

```tsx app/[locale]/[...slug]/page.tsx
import type { Metadata } from 'next';

type Props = { params: Promise<{ locale: string; slug: string[] }> };

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { locale, slug } = await params;
  // e.g. { 'pl-PL': '/pl/wakacje/grecja', 'de-DE': '/de/urlaub/griechenland', 'en-GB': '/en/holidays/greece' }
  const paths: Record<string, string> = await getLocalizedPaths(locale, slug);
  return {
    // Relative paths resolve against metadataBase set in the root layout
    alternates: {
      canonical: `/${locale}/${slug.join('/')}`,
      languages: { ...paths, 'x-default': paths['en-GB'] },
    },
  };
}
```
