@topic dom-what
title: Czym jest DOM (Document Object Model)
level: mid
tags: DOM, Document Object Model, drzewo, węzły, API
summary: DOM to obiektowa reprezentacja dokumentu HTML w postaci drzewa węzłów. Przeglądarka buduje ją z HTML, a JavaScript może ją czytać i zmieniać.

::: body
**DOM = Document Object Model**:

- **Document**: dotyczy dokumentu (strony HTML, także XML/SVG).
- **Object**: każdy fragment dokumentu to obiekt z właściwościami i metodami.
- **Model**: struktura drzewa opisująca relacje (rodzic, dzieci, rodzeństwo).

Drzewo składa się z **węzłów (nodes)**: `Document`, `Element` (`<div>`), `Text`, `Comment`, atrybuty. Korzeniem jest `document`, a jego elementem głównym `<html>`.

DOM to **API niezależne od języka** (standard WHATWG), a nie część JavaScriptu. JS korzysta z niego przez `document.querySelector`, `element.append`, `classList`, `addEventListener` itd.

DOM ≠ kod źródłowy HTML: przeglądarka poprawia błędy (dodaje brakujące `<tbody>`), a skrypty mogą go zmieniać. W DevTools zakładka **Elements** pokazuje aktualny DOM, a "View Source" oryginalny HTML.

::: code js
const list = document.querySelector('#offers');
const item = document.createElement('li');
item.textContent = 'Rzym, 7 nocy';        // safe: no HTML parsing
item.classList.add('offer');
list.append(item);

// Batch many insertions to avoid repeated layout work
const fragment = document.createDocumentFragment();
offers.forEach((o) => fragment.append(Object.assign(document.createElement('li'), { textContent: o.city })));
list.append(fragment);

::: qa
Q: Co to jest DOM?
A: Document Object Model: reprezentacja dokumentu HTML jako drzewa obiektów (węzłów), którą przeglądarka tworzy podczas parsowania. Udostępnia API, przez które JavaScript czyta i modyfikuje strukturę, treść i style strony.
Q: Czym różni się DOM od HTML?
A: HTML to tekst źródłowy. DOM to żywa struktura w pamięci zbudowana z tego tekstu, poprawiona przez parser i zmieniana przez skrypty. Po zmianach z JS DOM może się znacznie różnić od pierwotnego HTML.
Q: textContent vs innerHTML?
A: `textContent` wstawia czysty tekst (bezpieczne, szybkie). `innerHTML` parsuje HTML, co przy danych od użytkownika grozi XSS.

::: sources
- javascript.info: DOM tree | https://javascript.info/dom-nodes
- MDN: Document Object Model (DOM) | https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model

@topic dom-crp
title: Critical Rendering Path: od HTML do pikseli
level: mid
tags: CRP, DOM, CSSOM, render tree, layout, paint, composite
summary: Przeglądarka parsuje HTML do DOM, CSS do CSSOM, łączy je w render tree, oblicza układ (layout), maluje piksele (paint) i składa warstwy (composite).

::: body
1. **Parsowanie HTML → DOM**: bajty → znaki → tokeny → węzły → drzewo DOM. Parser działa przyrostowo. Zwykły `<script>` **zatrzymuje** parsowanie. Preload scanner w tle wyszukuje zasoby do pobrania (obrazy, CSS, JS).
2. **Parsowanie CSS → CSSOM**: drzewo reguł stylów z kaskadą i dziedziczeniem. CSS jest **render-blocking**: przeglądarka nie wyrenderuje strony bez kompletnego CSSOM.
3. **Render tree**: połączenie DOM i CSSOM, tylko **widoczne** elementy z obliczonymi stylami. Elementy z `display: none` i `<head>` nie trafiają do render tree (`visibility: hidden` trafia, bo zajmuje miejsce).
4. **Layout (reflow)**: obliczenie geometrii: pozycji i rozmiarów każdego elementu względem viewportu.
5. **Paint**: zamiana na piksele: tekst, kolory, obramowania, cienie, obrazy. Odbywa się na warstwach.
6. **Composite**: składanie warstw w odpowiedniej kolejności (GPU). `transform` i `opacity` często wymagają tylko tego kroku.

**Optymalizacja CRP**: mniej zasobów krytycznych, mniejsze pliki, krótsza ścieżka (mniej round-tripów). Konkretnie: inline krytycznego CSS, `defer` dla skryptów, preload najważniejszego obrazu (LCP), unikanie `@import` w CSS.

::: flow
HTML → DOM > CSS → CSSOM > DOM + CSSOM = Render Tree > Layout > Paint > Composite

::: analogy
Budowa domu: DOM to lista pomieszczeń, CSSOM to projekt wnętrz. Render tree to plan tylko tych pomieszczeń, które faktycznie budujesz. Layout to wymiarowanie ścian, paint to malowanie, a composite to złożenie gotowych prefabrykatów na miejscu.

::: qa
Q: Opisz proces renderowania strony przez przeglądarkę.
A: Parsowanie HTML do DOM i CSS do CSSOM, połączenie ich w render tree (tylko widoczne elementy ze stylami), layout (geometria), paint (piksele na warstwach) i composite (złożenie warstw na GPU). JavaScript może przerwać parsowanie i wymusić ponowne przeliczenie etapów.
Q: Dlaczego CSS blokuje renderowanie?
A: Bez pełnego CSSOM przeglądarka nie zna stylów, więc wyrenderowanie strony groziłoby "mignięciem" niestylowanej treści (FOUC). Dlatego CSS w `<head>` blokuje pierwszy render, ale nie parsowanie HTML.
Q: Czym różni się display: none od visibility: hidden w kontekście render tree?
A: `display: none` usuwa element z render tree (nie zajmuje miejsca, nie ma layoutu). `visibility: hidden` zostaje w render tree i zajmuje miejsce, tylko nie jest malowany.

- MDN: Critical rendering path | https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path
- web.dev: How browsers work | https://web.dev/articles/howbrowserswork
- web.dev: Understand the critical path | https://web.dev/learn/performance/understanding-the-critical-path

@topic dom-render-blocking
title: Zasoby blokujące: script, async, defer, type=module
level: mid
tags: async, defer, script, render-blocking, parser-blocking
summary: Zwykły script zatrzymuje parsowanie HTML. async pobiera w tle i wykonuje od razu po pobraniu, defer pobiera w tle i wykonuje po sparsowaniu dokumentu w kolejności.

::: body
| Atrybut | Pobieranie | Wykonanie | Kolejność | Kiedy |
|---|---|---|---|---|
| brak | blokuje parser | od razu | tak | unikaj w `<head>` |
| `async` | równolegle | zaraz po pobraniu (przerywa parser) | nie | niezależne skrypty: analityka, reklamy |
| `defer` | równolegle | po sparsowaniu HTML, przed `DOMContentLoaded` | tak | skrypty aplikacji |
| `type="module"` | równolegle | jak `defer` (domyślnie) | tak | nowoczesne ES modules |

CSS: `<link rel="stylesheet">` blokuje render. Style niekrytyczne można ładować z `media="print"` i przełączać albo przez preload. `@import` w CSS tworzy łańcuch zależności (wolniej).

Czcionki: `font-display: swap` pokazuje tekst od razu fontem zastępczym.

::: code html
<head>
  <link rel="preconnect" href="https://cdn.example.com" />
  <link rel="stylesheet" href="/critical.css" />
  <script src="/analytics.js" async></script>
  <script src="/app.js" defer></script>
  <script type="module" src="/main.js"></script>
</head>

::: qa
Q: Różnica między async a defer?
A: Oba pobierają skrypt równolegle z parsowaniem. `async` wykonuje go natychmiast po pobraniu (przerywając parser, bez gwarancji kolejności). `defer` wykonuje po sparsowaniu całego dokumentu, w kolejności w HTML, przed `DOMContentLoaded`.
Q: Dlaczego kiedyś umieszczano skrypty na końcu body?
A: Żeby nie blokowały parsowania i pierwszego renderu treści. Dziś ten sam efekt, z wcześniejszym rozpoczęciem pobierania, daje `defer` w `<head>`.

::: sources
- MDN: The script element | https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script
- web.dev: Render-blocking resources (Lighthouse) | https://developer.chrome.com/docs/lighthouse/performance/render-blocking-resources
- javascript.info: Scripts: async, defer | https://javascript.info/script-async-defer

@topic dom-reflow-repaint
title: Reflow, repaint, composite i layout thrashing
level: senior
tags: reflow, repaint, layout thrashing, transform, will-change
summary: Zmiana geometrii wymusza layout (reflow) i paint, zmiana wyglądu tylko paint, a transform i opacity mogą ominąć oba. Przeplatanie odczytów i zapisów DOM wymusza wielokrotne layouty.

::: body
Koszt zmiany zależy od etapu pipeline'u, który uruchamia:

- **Layout + Paint + Composite** (najdroższe): `width`, `height`, `top`, `margin`, `font-size`, dodanie elementu do DOM.
- **Paint + Composite**: `color`, `background`, `box-shadow`.
- **Tylko Composite** (najtańsze): `transform`, `opacity` (gdy element ma własną warstwę).

Animacje rób przez `transform` i `opacity`. `will-change: transform` promuje element na osobną warstwę (używaj oszczędnie: każda warstwa zużywa pamięć GPU).

**Forced synchronous layout / layout thrashing**: odczyt właściwości geometrycznej (`offsetHeight`, `getBoundingClientRect()`) po zapisie stylu zmusza przeglądarkę do natychmiastowego layoutu. W pętli to dziesiątki layoutów na klatkę. Rozwiązanie: najpierw wszystkie odczyty, potem wszystkie zapisy; `requestAnimationFrame`; `ResizeObserver`.

Pomocne CSS: `contain: layout paint` i `content-visibility: auto` (przeglądarka pomija renderowanie niewidocznych sekcji).

::: code js
// Layout thrashing: read-write-read-write forces layout on every iteration
cards.forEach((card) => {
  card.style.height = `${card.offsetWidth * 0.75}px`; // read then write, repeatedly
});

// Better: batch reads, then batch writes
const widths = cards.map((c) => c.offsetWidth);
requestAnimationFrame(() => {
  cards.forEach((c, i) => (c.style.height = `${widths[i] * 0.75}px`));
});

::: qa
Q: Czym różni się reflow od repaint?
A: Reflow (layout) to ponowne obliczenie geometrii elementów po zmianie wymiarów, pozycji lub struktury DOM; zwykle pociąga za sobą repaint. Repaint to ponowne malowanie pikseli bez zmiany układu (np. zmiana koloru). Reflow jest droższy.
Q: Dlaczego animować transform zamiast left/top?
A: `left`/`top` wymuszają layout i paint w każdej klatce. `transform` i `opacity` mogą być obsłużone przez compositor na GPU, bez layoutu i paintu, co daje płynne 60 fps i nie obciąża wątku głównego.
Q: Czym jest layout thrashing?
A: Przeplatanie zapisów stylów i odczytów geometrii w pętli, które zmusza przeglądarkę do wielu synchronicznych przeliczeń layoutu w jednej klatce. Naprawia się to grupowaniem odczytów i zapisów.

::: sources
- web.dev: Rendering performance | https://web.dev/articles/rendering-performance
- web.dev: Avoid large, complex layouts and layout thrashing | https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing
- web.dev: Stick to compositor-only properties | https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count
- web.dev: content-visibility | https://web.dev/articles/content-visibility

@topic dom-event-loop
title: Event loop: call stack, microtasks, macrotasks
level: mid
tags: event loop, microtask, macrotask, call stack, requestAnimationFrame
summary: JavaScript działa w jednym wątku. Event loop pobiera zadania z kolejek, gdy stos wywołań jest pusty: najpierw wszystkie mikrozadania, potem jedno makrozadanie i ewentualnie renderowanie.

::: body
- **Call stack**: aktualnie wykonywane funkcje. Dopóki nie jest pusty, nic innego się nie wykona (także renderowanie).
- **Web APIs**: timery, sieć, zdarzenia działają poza silnikiem JS i po zakończeniu kolejkują callbacki.
- **Task queue (macrotasks)**: `setTimeout`, `setInterval`, zdarzenia użytkownika, `MessageChannel`, I/O.
- **Microtask queue**: `Promise.then/catch/finally`, `await` (kontynuacja), `queueMicrotask`, `MutationObserver`.
- **Rendering**: `requestAnimationFrame` → style → layout → paint, zwykle co ok. 16,7 ms (60 Hz), gdy jest co odświeżyć.

Jedna iteracja pętli:

1. Wykonaj **jedno** makrozadanie.
2. Wykonaj **wszystkie** mikrozadania (także te dodane w trakcie).
3. Jeśli pora, wyrenderuj klatkę (rAF, style, layout, paint).
4. Powtórz.

Konsekwencje: długie zadanie (> 50 ms, "long task") blokuje interakcje i render, pogarszając **INP**. Dziel pracę (`scheduler.yield()`, `setTimeout`), przenoś ją do Web Workera. Nieskończona pętla mikrozadań zamrozi stronę.

::: flow
Call stack pusty > Wszystkie microtasks > Render (rAF, style, layout, paint) > Jeden macrotask > Wszystkie microtasks

::: code js
console.log('1 sync');
setTimeout(() => console.log('4 macrotask'), 0);
Promise.resolve().then(() => console.log('3 microtask'));
queueMicrotask(() => console.log('3b microtask'));
console.log('2 sync');
// Output: 1 sync, 2 sync, 3 microtask, 3b microtask, 4 macrotask

async function run() {
  console.log('A');
  await null;          // the rest of the function becomes a microtask
  console.log('C');
}
run();
console.log('B');      // A, B, C

::: qa
Q: Wyjaśnij event loop.
A: JS ma jeden wątek i stos wywołań. Operacje asynchroniczne wykonują się w Web APIs i po zakończeniu kolejkują callbacki. Gdy stos jest pusty, event loop wykonuje wszystkie mikrozadania (Promise), następnie przeglądarka może wyrenderować klatkę, a potem pobierane jest kolejne makrozadanie (np. setTimeout, zdarzenie).
Q: Co wykona się pierwsze: setTimeout(fn, 0) czy Promise.resolve().then(fn)?
A: Callback Promise. To mikrozadanie, a kolejka mikrozadań jest opróżniana w całości przed kolejnym makrozadaniem, takim jak `setTimeout`.
Q: Czym jest long task i dlaczego jest szkodliwy?
A: Zadanie na wątku głównym trwające dłużej niż 50 ms. Przez ten czas przeglądarka nie obsłuży kliknięć ani nie wyrenderuje klatki, co pogarsza INP i płynność. Rozwiązania: dzielenie pracy (`scheduler.yield`), Web Workers, mniej JS.

::: sources
- MDN: JavaScript execution model | https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model
- MDN: Using microtasks | https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide
- Jake Archibald: In The Loop (JSConf.Asia, video) | https://www.youtube.com/watch?v=cCOL7MC4Pl0
- Philip Roberts: What the heck is the event loop anyway? (video) | https://www.youtube.com/watch?v=8aGhZQkoFbQ

@topic dom-events
title: Zdarzenia: capturing, bubbling, delegacja
level: mid
tags: events, bubbling, capturing, delegation, preventDefault
summary: Zdarzenie przechodzi trzy fazy: capturing (z góry w dół), target, bubbling (z dołu w górę). Delegacja zdarzeń wykorzystuje bubbling: jeden listener na rodzicu obsługuje wiele dzieci.

::: body
- **Capturing**: od `window` w dół do celu. Listener z `{ capture: true }`.
- **Target**: zdarzenie na elemencie docelowym.
- **Bubbling**: od celu w górę. Domyślna faza dla `addEventListener`. Nie wszystkie zdarzenia "bąbelkują" (np. `focus`, ale jest `focusin`).
- `event.target`: element, na którym zdarzenie wystąpiło. `event.currentTarget`: element z listenerem.
- `stopPropagation()`: zatrzymuje propagację. `preventDefault()`: blokuje domyślne zachowanie (np. wysłanie formularza).
- **Delegacja**: jeden listener na kontenerze + `event.target.closest('.item')`. Mniej listenerów, działa dla dynamicznie dodanych elementów.
- Opcje: `{ once: true }`, `{ passive: true }` (listener nie wywoła `preventDefault`, co poprawia płynność scrolla), `{ signal }` (usuwanie przez AbortController).

React podpina listenery na korzeniu aplikacji (delegacja) i używa własnego systemu zdarzeń syntetycznych.

::: code js
document.querySelector('#offer-list').addEventListener('click', (e) => {
  const card = e.target.closest('[data-offer-id]');
  if (!card) return;
  openOffer(card.dataset.offerId);
});

const controller = new AbortController();
window.addEventListener('scroll', onScroll, { passive: true, signal: controller.signal });
controller.abort(); // removes the listener

::: qa
Q: Czym jest event bubbling?
A: Po obsłużeniu zdarzenia na elemencie docelowym zdarzenie "wędruje" w górę drzewa DOM przez kolejnych przodków, uruchamiając ich listenery. Przed nim zachodzi faza capturing (z góry w dół).
Q: Czym jest delegacja zdarzeń i jakie ma zalety?
A: Podpięcie jednego listenera na wspólnym rodzicu zamiast na każdym dziecku; element źródłowy rozpoznaje się przez `event.target` (np. `closest()`). Zalety: mniej pamięci, obsługa elementów dodanych dynamicznie, prostsze sprzątanie.
Q: target vs currentTarget?
A: `target` to element, który zapoczątkował zdarzenie (np. `<span>` w przycisku). `currentTarget` to element, do którego podpięty jest aktualnie wykonywany listener.

::: sources
- MDN: Event bubbling | https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Scripting/Event_bubbling
- MDN: addEventListener() | https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener
- javascript.info: Bubbling and capturing | https://javascript.info/bubbling-and-capturing

@topic dom-workers
title: Web Workers i Service Workers
level: senior
tags: Web Worker, Service Worker, offline, PWA, wątki
summary: Web Worker wykonuje ciężki JS w osobnym wątku, bez blokowania UI. Service Worker to proxy między stroną a siecią: cache, offline, push.

::: body
**Web Worker**:

- Osobny wątek, bez dostępu do DOM. Komunikacja przez `postMessage` (dane są kopiowane algorytmem structured clone lub przekazywane przez Transferable).
- Zastosowania: parsowanie dużych plików, kompresja obrazów, obliczenia, filtrowanie tysięcy rekordów. Biblioteka **Comlink** upraszcza API.

**Service Worker**:

- Działa w tle, niezależnie od karty, tylko przez HTTPS.
- Przechwytuje zapytania sieciowe (`fetch` event) i decyduje: sieć, cache, czy oba.
- Strategie: cache first (assety), network first (API), stale-while-revalidate.
- Umożliwia offline, powiadomienia push, background sync. Fundament PWA. Narzędzie: **Workbox**.
- Cykl życia: register → install → activate → fetch. Aktualizacja wymaga uwagi (stara wersja działa, dopóki są otwarte karty).

::: code js
// main.js
const worker = new Worker(new URL('./filter.worker.js', import.meta.url), { type: 'module' });
worker.postMessage({ offers, query });
worker.onmessage = (e) => render(e.data);

// filter.worker.js
self.onmessage = ({ data }) => {
  const result = data.offers.filter((o) => o.title.includes(data.query));
  self.postMessage(result);
};

::: qa
Q: Czym różni się Web Worker od Service Workera?
A: Web Worker to wątek do obliczeń, powiązany z konkretną stroną, bez dostępu do DOM. Service Worker to skrypt działający jako proxy sieciowe dla całego originu: przechwytuje requesty, zarządza cache, umożliwia offline i push, działa nawet po zamknięciu strony.
Q: Kiedy użyjesz Web Workera?
A: Gdy obliczenia na wątku głównym trwają na tyle długo, że blokują interakcje (long tasks): przetwarzanie dużych danych, obrazów, szyfrowanie, złożone wyszukiwanie.

::: sources
- MDN: Using Web Workers | https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers
- MDN: Service Worker API | https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API
- Chrome: Workbox | https://developer.chrome.com/docs/workbox

@topic dom-appcache-manifest
title: Plik manifestu w HTML5: AppCache (przestarzały) i Web App Manifest
level: mid
tags: manifest, AppCache, application cache, PWA, Web App Manifest, offline
summary: "Plik manifestu HTML5" to dawny Application Cache: lista plików do trzymania offline. Został usunięty z przeglądarek; zastąpiły go Service Workers. Dziś "manifest" oznacza zwykle Web App Manifest (manifest.json) dla PWA.

::: body
**Application Cache (AppCache)**, wprowadzony w HTML5:

- Atrybut `<html manifest="app.appcache">` wskazywał plik tekstowy z sekcjami **`CACHE`** (pliki do zapisania offline), **`NETWORK`** (zawsze z sieci) i **`FALLBACK`** (zamienniki, gdy brak sieci).
- Problemy: nieintuicyjne reguły aktualizacji (zmiana dowolnego pliku wymagała zmiany manifestu), strona zawsze ładowana najpierw z cache, trudne debugowanie. Jego wady szczegółowo opisał Jake Archibald w głośnym artykule na A List Apart (link w źródłach).
- **Usunięty**: Firefox od wersji 84 (grudzień 2020); Chrome wyłączył go w wersji 85 w bezpiecznych kontekstach, a całkowicie usunął w październiku 2021. Na rozmowie warto powiedzieć, że to technologia historyczna.

**Następcy:**

- **Service Worker + Cache API**: pełna, programowa kontrola nad cache i działaniem offline (strategie cache first, network first, stale-while-revalidate; Workbox).
- **Web App Manifest** (`<link rel="manifest" href="/manifest.webmanifest">`): plik JSON z nazwą aplikacji, ikonami, kolorami, `start_url` i trybem `display`. Pozwala zainstalować stronę jako aplikację (PWA). Nie służy do cache.

::: code html
<!-- Legacy AppCache (removed from browsers) -->
<html manifest="offline.appcache">

<!-- offline.appcache
CACHE MANIFEST
# v12
CACHE:
/css/app.css
/js/app.js
NETWORK:
/api/
FALLBACK:
/ /offline.html
-->

<!-- Modern: Web App Manifest for installable PWA -->
<link rel="manifest" href="/manifest.webmanifest" />

::: code json manifest.webmanifest
{
  "name": "Wakacje: moje rezerwacje",
  "short_name": "Rezerwacje",
  "start_url": "/moje-rezerwacje",
  "display": "standalone",
  "theme_color": "#2c56c9",
  "icons": [{ "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }]
}

::: qa
Q: Czym jest plik manifestu w HTML5?
A: W oryginalnym HTML5 był to manifest Application Cache: plik z sekcjami `CACHE`, `NETWORK` i `FALLBACK`, wskazywany atrybutem `manifest` na `<html>`, który pozwalał działać stronie offline. AppCache jest przestarzały i usunięty z przeglądarek na rzecz Service Workerów. Dziś "manifest" to zwykle Web App Manifest (JSON), który opisuje instalowalną aplikację PWA.
Q: Czym różni się Web App Manifest od Service Workera?
A: Manifest to statyczny opis aplikacji (nazwa, ikony, kolory, tryb wyświetlania), potrzebny do instalacji PWA. Service Worker to skrypt, który przechwytuje zapytania sieciowe i zarządza cache, zapewniając działanie offline i powiadomienia push.

@topic dom-storage
title: Storage w przeglądarce: cookies, localStorage, sessionStorage, IndexedDB
level: mid
tags: localStorage, sessionStorage, cookies, IndexedDB
summary: Cookies są wysyłane z każdym requestem i mogą być httpOnly. localStorage trwa do usunięcia, sessionStorage do zamknięcia karty. IndexedDB to asynchroniczna baza na większe dane.

::: body
| | Pojemność | Czas życia | Wysyłane do serwera | Dostęp z JS | API |
|---|---|---|---|---|---|
| Cookies | ok. 4 KB | `Expires`/`Max-Age` lub sesja | tak, automatycznie | nie, gdy `HttpOnly` | string |
| localStorage | ok. 5-10 MB | do usunięcia | nie | tak | synchroniczne |
| sessionStorage | ok. 5 MB | do zamknięcia karty | nie | tak | synchroniczne |
| IndexedDB | duża (zależna od dysku) | do usunięcia | nie | tak | asynchroniczne, transakcje |
| Cache API | duża | do usunięcia | nie | tak (głównie Service Worker) | Request/Response |

Atrybuty cookies: `HttpOnly` (niedostępne z JS, ochrona przed kradzieżą przez XSS), `Secure` (tylko HTTPS), `SameSite=Lax/Strict/None` (ochrona przed CSRF).

`localStorage` jest synchroniczne (blokuje wątek przy dużych danych) i dostępne dla każdego skryptu na stronie, więc nie trzymaj w nim tokenów sesyjnych ani danych wrażliwych.

::: qa
Q: localStorage vs sessionStorage vs cookies?
A: Cookies są małe i automatycznie dołączane do requestów (sesja, auth), mogą być `HttpOnly`. `localStorage` przechowuje dane bez limitu czasu, `sessionStorage` do zamknięcia karty; oba tylko po stronie klienta, synchroniczne, ok. 5 MB.
Q: Gdzie trzymać token uwierzytelniający?
A: Najbezpieczniej w cookie `HttpOnly; Secure; SameSite`, bo skrypt (także złośliwy przez XSS) go nie odczyta. `localStorage` jest dostępny dla każdego JS na stronie. Wybór pociąga konieczność ochrony przed CSRF (SameSite, tokeny CSRF).

::: sources
- MDN: Web Storage API | https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API
- MDN: Using HTTP cookies | https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies
- MDN: IndexedDB API | https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API
