@topic sec-xss
title: XSS (Cross-Site Scripting)
level: mid
tags: XSS, dangerouslySetInnerHTML, sanitization, innerHTML
summary: Atakujący wstrzykuje złośliwy skrypt, który wykonuje się w przeglądarce ofiary w kontekście Twojej strony: może wykraść dane, wykonać akcje lub podmienić treść.

::: body
Rodzaje:

- **Stored**: skrypt zapisany w bazie (np. w opinii o hotelu) i wyświetlany innym.
- **Reflected**: skrypt w URL lub parametrze, odbity w odpowiedzi.
- **DOM-based**: kod frontu wstawia niezaufane dane do DOM (`innerHTML`, `document.write`, `location.hash`).

Obrona:

- **Escapowanie przy renderowaniu**: React domyślnie escapuje wartości w JSX. Ryzyko pojawia się przy `dangerouslySetInnerHTML`, `href={userUrl}` (schemat `javascript:`), `innerHTML`, `eval`, `new Function`.
- **Sanitizacja** HTML od użytkownika (np. DOMPurify), gdy musisz go wyrenderować.
- Walidacja URL: dopuszczaj tylko `http:` i `https:`.
- **Content Security Policy** jako druga linia obrony.
- Cookies sesyjne `HttpOnly` (skrypt ich nie odczyta).
- Trusted Types (Chrome) wymuszają bezpieczne API dla "sinków" DOM.

::: code tsx
// Safe: React escapes text content
<p>{review.text}</p>

// Dangerous: raw HTML from users
<div dangerouslySetInnerHTML={{ __html: review.html }} />

// Safer: sanitize first
import DOMPurify from 'dompurify';
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(review.html) }} />

// Validate user-provided URLs
const safeHref = (url: string) => (/^https?:\/\//i.test(url) ? url : '#');

::: qa
Q: Czym jest XSS i jak się przed nim bronić w React?
A: Wstrzyknięciem i wykonaniem złośliwego skryptu w kontekście strony. React escapuje wartości w JSX, więc główne ryzyka to `dangerouslySetInnerHTML`, niezwalidowane URL-e w `href`/`src` i bezpośrednie operacje na DOM. Obrona: unikanie surowego HTML, sanitizacja (DOMPurify), walidacja URL, CSP i cookies `HttpOnly`.
Q: Czy React całkowicie chroni przed XSS?
A: Nie. Chroni przy wstawianiu tekstu w JSX, ale nie przy `dangerouslySetInnerHTML`, linkach `javascript:`, bibliotekach operujących na DOM, SSR z niebezpiecznym wstrzykiwaniem danych do skryptów ani przy zależnościach third-party.

::: sources
- MDN: Cross-site scripting (XSS) | https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS
- OWASP: XSS Prevention Cheat Sheet | https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html
- React: dangerouslySetInnerHTML | https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html

@topic sec-csrf
title: CSRF (Cross-Site Request Forgery)
level: mid
tags: CSRF, SameSite, cookies, token
summary: Złośliwa strona sprawia, że przeglądarka zalogowanego użytkownika wysyła żądanie do Twojego serwisu razem z jego cookies. Serwer myśli, że to prawdziwa akcja użytkownika.

::: body
Warunki ataku: uwierzytelnienie przez cookies (dołączane automatycznie) i akcja zmieniająca stan (np. `POST /transfer`), którą da się wywołać z innej strony (formularz, obrazek).

Obrona:

- **`SameSite=Lax`** (domyślne w nowoczesnych przeglądarkach) lub `Strict` dla cookies sesyjnych: cookie nie jest wysyłane przy żądaniach cross-site (Lax dopuszcza nawigację GET).
- **Tokeny CSRF** (synchronizer token, double submit cookie) dla formularzy.
- Sprawdzanie nagłówków `Origin` / `Sec-Fetch-Site`.
- `GET` nigdy nie zmienia stanu.
- Tokeny w nagłówku `Authorization` (zamiast cookies) nie są podatne na CSRF, ale jeśli trzymasz je w `localStorage`, stają się podatne na kradzież przez XSS.

CORS **nie chroni** przed CSRF: blokuje odczyt odpowiedzi, ale żądanie i tak może dotrzeć do serwera.

::: qa
Q: Czym jest CSRF i jak mu zapobiec?
A: Atakiem, w którym obca strona wysyła żądanie do Twojego serwisu z cookies zalogowanego użytkownika. Zapobiegamy przez `SameSite` na cookies, tokeny CSRF, weryfikację `Origin`, nieużywanie GET do zmian stanu.
Q: XSS vs CSRF?
A: XSS wykonuje kod atakującego w Twojej stronie (może zrobić wszystko, co użytkownik). CSRF nie wykonuje kodu w Twojej stronie; wykorzystuje automatyczne wysyłanie cookies, żeby wywołać akcję z zewnątrz. XSS zwykle omija zabezpieczenia CSRF.

::: sources
- MDN: Cross-site request forgery (CSRF) | https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF
- OWASP: CSRF Prevention Cheat Sheet | https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

@topic sec-csp
title: Content Security Policy (CSP)
level: senior
tags: CSP, nagłówki, nonce, bezpieczeństwo
summary: Nagłówek, w którym deklarujesz, skąd strona może ładować skrypty, style, obrazy i połączenia. Nawet jeśli atakujący wstrzyknie skrypt, przeglądarka go nie wykona.

::: body
- `Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-abc123'; img-src 'self' https://cdn.example.com; connect-src 'self' https://api.example.com`.
- **Strict CSP** oparta na `nonce` lub hashach jest skuteczniejsza niż długie listy domen.
- Unikaj `'unsafe-inline'` i `'unsafe-eval'` dla skryptów.
- **`Content-Security-Policy-Report-Only`** + `report-to`: testujesz politykę bez blokowania i zbierasz naruszenia przed wdrożeniem.
- `frame-ancestors 'none'` chroni przed clickjackingiem (następca `X-Frame-Options`).

Next.js pozwala generować nonce w proxy/middleware i przekazać go do skryptów.

::: qa
Q: Czym jest CSP i przed czym chroni?
A: Nagłówkiem HTTP definiującym dozwolone źródła zasobów (skrypty, style, obrazy, połączenia, ramki). Ogranicza skutki XSS (wstrzyknięty skrypt spoza polityki nie wykona się), clickjackingu i nieautoryzowanego wycieku danych.
Q: Jak bezpiecznie wdrożyć CSP w istniejącej aplikacji?
A: Najpierw tryb `Report-Only` z raportowaniem, analiza naruszeń (skrypty third-party, inline), wprowadzenie nonce dla skryptów, dopiero potem tryb wymuszający. Za: silna ochrona przed XSS. Przeciw: praca przy integracjach third-party. Długofalowo: każdy nowy skrypt wymaga świadomej decyzji.

::: sources
- MDN: Content Security Policy (CSP) | https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP
- web.dev: Mitigate XSS with a strict CSP | https://web.dev/articles/strict-csp

@topic sec-auth-storage
title: Sesja i tokeny: gdzie je trzymać (JWT, cookies)
level: senior
tags: JWT, cookies, localStorage, auth, refresh token
summary: Najbezpieczniej trzymać sesję w cookie HttpOnly, Secure, SameSite. Tokeny w localStorage są wygodne, ale każdy skrypt na stronie (także z XSS) może je odczytać.

::: body
| | Cookie HttpOnly | localStorage / sessionStorage | Pamięć JS |
|---|---|---|---|
| Kradzież przez XSS | trudna (JS nie odczyta) | łatwa | możliwa w trakcie sesji |
| CSRF | trzeba chronić (SameSite, token) | brak ryzyka | brak ryzyka |
| Przeżywa odświeżenie | tak | tak | nie |
| Wysyłane automatycznie | tak | nie (ręczny nagłówek) | nie |

- **JWT** to podpisany (nie zaszyfrowany!) token z danymi (claims). Każdy może go zdekodować, ale nie zmienić bez klucza. Nie wkładaj do niego danych wrażliwych. Trudno go unieważnić przed wygaśnięciem, dlatego krótki czas życia + refresh token.
- Typowy wzorzec: krótki access token + refresh token w cookie `HttpOnly`, rotacja refresh tokenów.
- **BFF**: serwer (np. Next.js) trzyma tokeny, a przeglądarka ma tylko cookie sesyjne. Najbezpieczniejsze dla SPA.

::: qa
Q: Gdzie trzymać JWT w aplikacji przeglądarkowej?
A: Preferowane jest cookie `HttpOnly; Secure; SameSite=Lax/Strict` (odporne na odczyt przez XSS) z ochroną CSRF, najlepiej w architekturze BFF. `localStorage` jest prostsze, ale każdy wstrzyknięty skrypt odczyta token. Konsekwencje: cookies wymagają konfiguracji CORS z credentials i ochrony CSRF; localStorage zwiększa skutki ewentualnego XSS.
Q: Czy JWT jest zaszyfrowany?
A: Standardowy JWT (JWS) jest tylko podpisany i zakodowany w base64url. Treść może odczytać każdy, podpis gwarantuje jedynie integralność. Do poufności służy JWE lub po prostu nieumieszczanie wrażliwych danych.

::: sources
- OWASP: Session Management Cheat Sheet | https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
- MDN: Using HTTP cookies (security) | https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies
- jwt.io: Introduction to JSON Web Tokens | https://www.jwt.io/introduction

@topic sec-supply-chain
title: Bezpieczeństwo zależności (supply chain)
level: senior
tags: npm audit, dependencies, supply chain, Dependabot
summary: Każda paczka npm to kod, który uruchamiasz u siebie i u użytkowników. Ataki na łańcuch dostaw (przejęte konta, złośliwe wersje, typosquatting) są realnym zagrożeniem.

::: body
- Commituj lockfile i instaluj w CI deterministycznie (`npm ci`).
- Automatyczne aktualizacje z review: Dependabot, Renovate. `npm audit` / `pnpm audit` w CI.
- Ogranicz skrypty instalacyjne (`ignore-scripts`, w pnpm domyślnie trzeba je jawnie dopuścić), zwłaszcza w CI.
- Sprawdzaj nowe zależności: popularność, utrzymanie, rozmiar, liczbę zależności przechodnich. Czy naprawdę potrzebujesz paczki do 10 linii kodu?
- Opóźnij przyjmowanie świeżo opublikowanych wersji (np. ustawienia minimalnego wieku wydania w menedżerze pakietów lub Renovate), bo złośliwe wersje są zwykle szybko wykrywane.
- Skrypty third-party na stronie: Subresource Integrity (`integrity`) dla plików z CDN, CSP.

::: qa
Q: Jak ograniczasz ryzyko związane z zależnościami npm?
A: Lockfile i `npm ci`, automatyczne aktualizacje z review (Renovate/Dependabot), audyt w CI, ograniczenie skryptów instalacyjnych, weryfikacja nowych paczek przed dodaniem, minimalizacja liczby zależności, SRI i CSP dla skryptów zewnętrznych.

::: sources
- npm Docs: npm audit | https://docs.npmjs.com/cli/v11/commands/npm-audit
- OWASP: NPM Security Cheat Sheet | https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html
- MDN: Subresource Integrity | https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity

@quiz
Q: Które miejsce w React jest typowym źródłem XSS?
- Wstawienie {text} w JSX
+ dangerouslySetInnerHTML z danymi od użytkownika
- useState
- className
E: JSX escapuje tekst; surowy HTML omija tę ochronę.
T: sec-xss

Q: Które ustawienie cookie chroni przed CSRF?
- HttpOnly
+ SameSite=Lax/Strict
- Secure
- Max-Age
E: SameSite ogranicza wysyłanie cookies przy żądaniach cross-site. HttpOnly chroni przed odczytem przez JS.
T: sec-csrf

Q: Czy treść standardowego JWT jest zaszyfrowana?
- Tak, zawsze
+ Nie, jest tylko podpisana i zakodowana base64url
- Tylko w HTTPS
- Tylko claim "sub"
E: Każdy może odczytać payload; podpis gwarantuje integralność, nie poufność.
T: sec-auth-storage

Q: Do czego służy tryb Content-Security-Policy-Report-Only?
+ Do testowania polityki i zbierania naruszeń bez blokowania zasobów
- Do wyłączenia CSP w dev
- Do raportowania błędów JS
- Do blokowania wszystkich skryptów
E: Pozwala bezpiecznie przygotować politykę przed wymuszeniem.
T: sec-csp
