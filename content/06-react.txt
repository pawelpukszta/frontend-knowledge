@topic react-render-commit
title: Render i commit: kiedy komponent się renderuje
level: mid
tags: render, commit, re-render, state
summary: Render to wywołanie funkcji komponentu i obliczenie nowego JSX. Commit to naniesienie różnic na prawdziwy DOM. Re-render nie oznacza zmiany w DOM.

::: body
Trzy kroki (jak w restauracji: zamówienie, gotowanie, podanie):

1. **Trigger**: pierwszy render (`createRoot().render`) albo zmiana stanu (`setState`) w komponencie lub jego przodku.
2. **Render**: React wywołuje funkcje komponentów i buduje nowe drzewo elementów. To czyste obliczenie, bez dotykania DOM.
3. **Commit**: React porównuje nowe drzewo z poprzednim i nanosi **minimalne zmiany** na DOM. Potem przeglądarka maluje ekran i uruchamiają się efekty.

Komponent renderuje się ponownie, gdy:

- zmieni się **jego stan**,
- **rodzic się przerenderuje** (domyślnie wszystkie dzieci też, niezależnie od props!),
- zmieni się **kontekst**, którego używa.

Zmiana props sama w sobie nie jest przyczyną; props zmieniają się, bo rodzic się przerenderował. `setState` z tą samą wartością (wg `Object.is`) jest pomijany. Aktualizacje stanu są **batchowane** (od React 18 także w Promise i timeoutach).

W trybie dev `StrictMode` wywołuje komponenty i efekty podwójnie, żeby wykryć nieczyste funkcje.

::: flow
Trigger (setState) > Render (wywołanie komponentów) > Reconciliation (diff) > Commit (zmiany w DOM) > Paint > useEffect

::: qa
Q: Kiedy komponent React się re-renderuje?
A: Gdy zmienia się jego stan, gdy przerenderuje się jego rodzic (domyślnie całe poddrzewo) lub gdy zmieni się wartość kontekstu, który czyta. Zmiana props wynika z re-renderu rodzica.
Q: Czy re-render zawsze zmienia DOM?
A: Nie. Render to tylko obliczenie JSX. Jeśli wynik jest taki sam, faza commit nic nie zmieni w DOM. Koszt re-renderu to czas wykonania funkcji komponentów i porównania.
Q: Co to jest batching?
A: Grupowanie wielu `setState` w jedną aktualizację i jeden render. Od React 18 działa automatycznie wszędzie, także w Promise, `setTimeout` i natywnych event handlerach.

::: sources
- React: Render and Commit | https://react.dev/learn/render-and-commit
- React: State as a Snapshot | https://react.dev/learn/state-as-a-snapshot
- React: Queueing a Series of State Updates | https://react.dev/learn/queueing-a-series-of-state-updates

@topic react-reconciliation
title: Virtual DOM, reconciliation i klucze
level: mid
tags: Virtual DOM, reconciliation, diffing, key, Fiber
summary: React trzyma lekką reprezentację UI w pamięci i przy zmianie porównuje ją z poprzednią (reconciliation), żeby zaktualizować tylko to, co się zmieniło w DOM. Klucze pomagają dopasować elementy list.

::: body
**Virtual DOM**: drzewo zwykłych obiektów JS opisujących UI (wynik JSX). Tworzenie ich jest tanie, operacje na prawdziwym DOM są drogie.

**Reconciliation** (heurystyki O(n)):

- Inny **typ elementu** na tej samej pozycji (`<div>` → `<span>`, `ComponentA` → `ComponentB`): React niszczy całe poddrzewo, **tracąc stan**, i tworzy nowe.
- Ten sam typ: aktualizuje atrybuty i rekurencyjnie porównuje dzieci.
- **Listy**: `key` identyfikuje element między renderami. Bez stabilnego klucza React dopasowuje elementy po indeksie.

**Fiber**: silnik React od wersji 16, który dzieli pracę renderowania na małe jednostki i pozwala ją przerywać i priorytetyzować (Concurrent rendering, `useTransition`).

Stan jest przywiązany do **pozycji w drzewie**, a nie do komponentu. Zmiana `key` to sposób na świadomy reset stanu komponentu.

::: code tsx
// Bad: index as key - state (e.g. input value) jumps between items after reorder/delete
{items.map((item, i) => <Row key={i} item={item} />)}

// Good: stable id from data
{items.map((item) => <Row key={item.id} item={item} />)}

// Reset a form when a different offer is selected
<BookingForm key={offer.id} offer={offer} />

::: pitfalls
- `key={Math.random()}`: element jest odtwarzany przy każdym renderze (utrata stanu, słaba wydajność).
- Definiowanie komponentu wewnątrz innego komponentu: przy każdym renderze to nowy typ, więc React niszczy i odtwarza jego poddrzewo.

::: qa
Q: Czym jest Virtual DOM i po co React go używa?
A: Reprezentacją UI w postaci obiektów JS. React tworzy nowe drzewo przy każdym renderze, porównuje z poprzednim i nanosi na prawdziwy DOM tylko różnice. Daje deklaratywny model programowania przy akceptowalnej wydajności.
Q: Dlaczego nie używać indeksu jako key?
A: Przy zmianie kolejności, wstawianiu lub usuwaniu elementów indeks przypisuje się innym danym, więc React błędnie dopasowuje stan komponentów (np. wartości inputów) i wykonuje zbędne aktualizacje. Indeks jest OK tylko dla statycznych list.
Q: Jak zresetować stan komponentu?
A: Zmienić jego `key`. React potraktuje go jako nowy element i utworzy go od zera.

::: sources
- React: Preserving and Resetting State | https://react.dev/learn/preserving-and-resetting-state
- React: Rendering Lists (keys) | https://react.dev/learn/rendering-lists
- legacy.reactjs.org: Reconciliation | https://legacy.reactjs.org/docs/reconciliation.html

@topic react-memo
title: React.memo
level: mid
tags: memo, re-render, props, optymalizacja
summary: memo opakowuje komponent tak, aby pomijał re-render, gdy jego props są płytko równe poprzednim. Działa tylko, jeśli props mają stabilne referencje.

::: body
- `memo(Component)` porównuje każdy prop przez `Object.is`. Jeśli wszystkie są równe, React używa poprzedniego wyniku.
- Nie blokuje re-renderu wywołanego **własnym stanem** komponentu ani **kontekstem**.
- Działa tylko, gdy props są stabilne. Nowy obiekt, tablica lub funkcja tworzone w rodzicu przy każdym renderze niweczą `memo`. Tu wchodzą `useMemo` i `useCallback`.

Kiedy ma sens: komponent renderuje się często z tymi samymi props **i** jego render jest kosztowny (duże listy, wykresy, edytory). Zmierz przed i po w React DevTools Profiler.

::: code tsx
const OfferList = memo(function OfferList({ offers, onSelect }: Props) {
  return offers.map((o) => <OfferCard key={o.id} offer={o} onSelect={onSelect} />);
});

function Page() {
  const [query, setQuery] = useState('');
  const offers = useOffers();
  const onSelect = useCallback((id: string) => navigate(`/offer/${id}`), []); // stable reference
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <OfferList offers={offers} onSelect={onSelect} /> {/* skipped while typing */}
    </>
  );
}

::: qa
Q: Jak działa React.memo?
A: Opakowuje komponent i przy re-renderze rodzica porównuje płytko (Object.is) nowe props z poprzednimi. Jeśli są równe, pomija render. Nie chroni przed zmianami własnego stanu i kontekstu.
Q: Dlaczego memo czasem "nie działa"?
A: Bo rodzic przekazuje nowe referencje przy każdym renderze: inline obiekty (`style={{}}`), tablice, funkcje strzałkowe, a także `children` jako JSX. Trzeba je ustabilizować (`useMemo`/`useCallback`) albo zmienić strukturę komponentów.

::: sources
- React: memo | https://react.dev/reference/react/memo
- React Developer Tools (Profiler) | https://react.dev/learn/react-developer-tools

@topic react-usememo-usecallback
title: useMemo i useCallback: kiedy tak, kiedy nie
level: mid
tags: useMemo, useCallback, memoizacja, referencje, performance
summary: useMemo zapamiętuje wynik obliczenia, useCallback zapamiętuje funkcję. Oba służą do dwóch rzeczy: unikania drogich obliczeń i utrzymywania stabilnych referencji. W innych przypadkach tylko dokładają kosztu.

::: body
- `useMemo(() => compute(a, b), [a, b])`: przelicza tylko, gdy zmienią się zależności.
- `useCallback(fn, [deps])` to to samo co `useMemo(() => fn, [deps])`: zwraca tę samą referencję funkcji między renderami.

**Kiedy używać:**

1. **Kosztowne obliczenie** (filtrowanie/sortowanie tysięcy elementów, parsowanie), mierzalnie wolne. Orientacyjnie: gdy w Profilerze zajmuje ok. 1 ms lub więcej.
2. **Stabilna referencja** przekazywana do komponentu w `memo`.
3. **Zależność innego hooka** (`useEffect`, `useMemo`), żeby efekt nie odpalał się przy każdym renderze.
4. Wartość `value` providera Context.

**Kiedy NIE używać:**

- Proste obliczenia (`a + b`, mapowanie 10 elementów): koszt porównania zależności i pamięci jest większy niż zysk.
- Funkcja przekazywana do zwykłego elementu DOM (`<button onClick>`) lub komponentu bez `memo`: stabilna referencja nic nie daje.
- "Na wszelki wypadek" wszędzie: gorsza czytelność, łatwe do przeoczenia błędne zależności.

**React Compiler** (stabilny od 2025) automatycznie memoizuje komponenty i wartości, więc w projektach z kompilatorem ręczne `useMemo`/`useCallback` są potrzebne rzadko (np. jako precyzyjna kontrola zależności efektu).

::: code tsx
function Offers({ offers, query }: { offers: Offer[]; query: string }) {
  // Worth it: filtering and sorting thousands of items
  const visible = useMemo(
    () => offers.filter((o) => o.title.includes(query)).toSorted((a, b) => a.price - b.price),
    [offers, query],
  );

  // Not worth it: trivial computation
  const count = visible.length; // just compute it

  // Worth it only because MemoMap is wrapped in memo
  const onPinClick = useCallback((id: string) => setSelected(id), []);
  return <MemoMap offers={visible} onPinClick={onPinClick} />;
}

::: pitfalls
- Brakujące zależności: zapamiętana wartość jest nieaktualna (stale closure). Włącz regułę `react-hooks/exhaustive-deps`.
- Zależność będąca nowym obiektem przy każdym renderze: memoizacja nigdy nie trafia w cache.
- Traktowanie `useMemo` jako gwarancji semantycznej. To optymalizacja; React może wyrzucić cache.

::: qa
Q: Czym różni się useMemo od useCallback?
A: `useMemo` zapamiętuje wynik wywołania funkcji (wartość), `useCallback` zapamiętuje samą funkcję (referencję). `useCallback(fn, deps)` jest równoważne `useMemo(() => fn, deps)`.
Q: Kiedy nie warto używać useMemo i useCallback?
A: Przy tanich obliczeniach i gdy stabilna referencja niczego nie zmienia (funkcja trafia do elementu DOM lub komponentu bez memo, wartość nie jest zależnością hooka). Wtedy dodają koszt porównań, pamięci i złożoności kodu bez zysku.
Q: Czy useCallback sprawia, że funkcja nie jest tworzona na nowo?
A: Nie. Funkcja inline jest tworzona przy każdym renderze i tak; `useCallback` tylko zwraca poprzednią referencję, jeśli zależności się nie zmieniły. Zysk pojawia się dopiero tam, gdzie ktoś porównuje referencje (memo, zależności hooków).
Q: Jak React Compiler zmienia podejście do memoizacji?
A: Kompilator analizuje komponenty w czasie buildu i automatycznie memoizuje wartości, funkcje i JSX. Ręczna memoizacja staje się wyjątkiem. Warunek: kod musi przestrzegać Rules of React (czyste komponenty, brak mutacji props i stanu).

::: sources
- React: useMemo | https://react.dev/reference/react/useMemo
- React: useCallback | https://react.dev/reference/react/useCallback
- Kent C. Dodds: When to useMemo and useCallback | https://kentcdodds.com/blog/usememo-and-usecallback

@topic react-before-memo
title: Optymalizacja bez memo: przesuń stan w dół, podnieś treść w górę
level: senior
tags: composition, children, state colocation, performance
summary: Zanim sięgniesz po memo, zmień strukturę komponentów. Stan przeniesiony niżej lub treść przekazana przez children często usuwa zbędne re-rendery bez żadnej memoizacji.

::: body
Dwie techniki z artykułu Dana Abramova "Before You memo()":

1. **Move state down (colocation)**: jeśli stan używa tylko mały fragment UI, wydziel ten fragment do osobnego komponentu razem ze stanem. Zmiana stanu re-renderuje wtedy tylko ten mały komponent.
2. **Lift content up (children as props)**: jeśli komponent ze stanem musi owijać dużą część drzewa, przekaż tę część jako `children`. Elementy `children` są tworzone przez rodzica wyżej, więc zmiana stanu w wrapperze ich nie re-renderuje (ta sama referencja elementu).

Dodatkowo: dziel duże komponenty, trzymaj Context providery nisko, wirtualizuj długie listy (TanStack Virtual), a dla kosztownych aktualizacji używaj `useTransition`/`useDeferredValue`.

::: code tsx
// Before: typing re-renders ExpensiveTree
function App() {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input value={color} onChange={(e) => setColor(e.target.value)} />
      <ExpensiveTree />
    </div>
  );
}

// After: content lifted up as children - ExpensiveTree is not re-rendered
function ColorPicker({ children }: { children: React.ReactNode }) {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input value={color} onChange={(e) => setColor(e.target.value)} />
      {children}
    </div>
  );
}
const App = () => <ColorPicker><ExpensiveTree /></ColorPicker>;

::: qa
Q: Jak ograniczyć re-rendery bez memo?
A: Przenieść stan bliżej miejsca użycia (state colocation), a gdy komponent ze stanem musi owijać dużą część UI, przekazać ją przez `children`. Elementy utworzone wyżej nie re-renderują się przy zmianie stanu wrappera.
Q: Czym są useTransition i useDeferredValue?
A: Narzędzia concurrent rendering. `useTransition` oznacza aktualizację jako niepilną, więc pilne interakcje (wpisywanie) nie są blokowane. `useDeferredValue` daje "opóźnioną" wersję wartości do kosztownego renderu, podczas gdy input aktualizuje się natychmiast.

::: sources
- Dan Abramov: Before You memo() | https://overreacted.io/before-you-memo/
- React: useTransition | https://react.dev/reference/react/useTransition
- React: useDeferredValue | https://react.dev/reference/react/useDeferredValue

@topic react-compiler
title: React Compiler
level: senior
tags: React Compiler, memoization, build, Rules of React
summary: Narzędzie działające w czasie buildu, które automatycznie memoizuje komponenty i hooki. Zastępuje większość ręcznego useMemo, useCallback i memo.

::: body
- Działa jako plugin Babel (także w Vite, Next.js, Expo). W Next.js włączasz opcją `reactCompiler: true`.
- Analizuje kod i wstawia memoizację na poziomie pojedynczych wartości i fragmentów JSX, dokładniej niż zrobiłby to człowiek.
- Wymaga przestrzegania **Rules of React**: komponenty i hooki muszą być czyste, bez mutowania props, stanu i wartości zwracanych przez hooki. Komponenty łamiące zasady są pomijane.
- Plugin ESLint `eslint-plugin-react-hooks` zawiera reguły wykrywające problemy, które uniemożliwiają kompilację.

Decyzja dla zespołu: włączenie kompilatora w istniejącym projekcie. Za: mniej ręcznej optymalizacji, mniej błędów z zależnościami, lepsza domyślna wydajność. Przeciw: zależność od kroku buildu, potrzeba naprawy kodu łamiącego zasady, trudniejsze debugowanie nietypowych przypadków. Długofalowo: kod prostszy, a wiedza o memoizacji nadal potrzebna przy analizie problemów.

::: qa
Q: Czym jest React Compiler?
A: Kompilatorem działającym w czasie buildu, który automatycznie dodaje memoizację komponentów, wartości i funkcji. Dzięki temu ręczne `memo`, `useMemo` i `useCallback` są potrzebne rzadko.
Q: Jakie warunki musi spełniać kod, żeby kompilator go zoptymalizował?
A: Przestrzegać Rules of React: czyste komponenty (ten sam input daje ten sam output), brak mutacji props, stanu i wartości z hooków w trakcie renderu, hooki wywoływane na najwyższym poziomie.

::: sources
- React: React Compiler | https://react.dev/learn/react-compiler
- React: Rules of React | https://react.dev/reference/rules
- Next.js: reactCompiler | https://nextjs.org/docs/app/api-reference/config/next-config-js/reactCompiler

@topic react-effects
title: useEffect i "You Might Not Need an Effect"
level: mid
tags: useEffect, side effects, cleanup, synchronizacja
summary: useEffect służy do synchronizacji z systemami zewnętrznymi (API przeglądarki, subskrypcje, widgety). Nie używaj go do wyliczania danych z props ani do reagowania na zdarzenia użytkownika.

::: body
Efekt uruchamia się **po commicie** (po malowaniu ekranu). Funkcja zwrócona z efektu to **cleanup**, wywoływany przed następnym uruchomieniem i przy odmontowaniu.

Dobre zastosowania: subskrypcje (WebSocket, `addEventListener`), integracja z bibliotekami spoza React (mapa, wykres), synchronizacja z `document.title`, pobieranie danych (choć lepiej przez TanStack Query lub framework).

Kiedy **nie potrzebujesz** efektu:

- **Wyliczanie danych**: `fullName = first + ' ' + last` licz w trakcie renderu, nie w `useEffect` + `setState` (dodatkowy render i ryzyko niespójności).
- **Reakcja na zdarzenie**: logikę po kliknięciu umieść w event handlerze.
- **Reset stanu przy zmianie props**: użyj `key`.
- **Kosztowne obliczenie**: `useMemo`.

`useLayoutEffect` uruchamia się synchronicznie przed malowaniem: do pomiaru DOM (np. pozycji tooltipa), żeby uniknąć migotania.

::: code tsx
// Bad: derived state through an effect (extra render)
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce((s, i) => s + i.price, 0)), [items]);

// Good: compute during render
const total = items.reduce((s, i) => s + i.price, 0);

// Good use: subscribing to an external system with cleanup
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, []);

::: qa
Q: Do czego służy useEffect?
A: Do synchronizacji komponentu z czymś spoza React: API przeglądarki, subskrypcje, zewnętrzne biblioteki, sieć. Uruchamia się po renderze i commicie, a funkcja cleanup sprząta przed kolejnym uruchomieniem i przy odmontowaniu.
Q: Podaj przykłady niepotrzebnych efektów.
A: Przeliczanie stanu z props (licz w renderze), reagowanie na kliknięcie (użyj event handlera), resetowanie stanu przy zmianie ID (użyj `key`), łańcuchy efektów ustawiających stan jeden po drugim.
Q: Różnica między useEffect a useLayoutEffect?
A: `useEffect` działa asynchronicznie po malowaniu ekranu. `useLayoutEffect` synchronicznie po zmianach DOM, ale przed malowaniem, więc blokuje paint. Używaj go tylko do pomiarów i poprawek układu, które muszą być widoczne w pierwszej klatce.

::: sources
- React: You Might Not Need an Effect | https://react.dev/learn/you-might-not-need-an-effect
- React: Synchronizing with Effects | https://react.dev/learn/synchronizing-with-effects
- React: useLayoutEffect | https://react.dev/reference/react/useLayoutEffect

@topic react-custom-hooks
title: Custom hooks
level: mid
tags: custom hooks, reużywalność logiki, Rules of Hooks
summary: Custom hook to funkcja zaczynająca się od use, która składa inne hooki. Współdzieli logikę, a nie stan: każde wywołanie ma własny stan.

::: body
- Nazwa zaczyna się od `use`, dzięki czemu linter pilnuje **Rules of Hooks**: wywołuj hooki tylko na najwyższym poziomie komponentu lub innego hooka, nie w warunkach i pętlach.
- Dwa komponenty używające tego samego hooka mają **niezależny** stan. Do współdzielenia stanu potrzebujesz Context lub store'a.
- Dobre hooki mają jedną odpowiedzialność i jasne API: `useDebounce`, `useMediaQuery`, `useOnlineStatus`, `useLocalStorage`.
- Hook dla każdego `useEffect` to też sposób na czytelność: nazwa mówi, co efekt robi.

::: code ts
export function useDebouncedValue<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel if value changes before the delay
  }, [value, delay]);
  return debounced;
}

// usage
const query = useDebouncedValue(input, 300);
const { data } = useQuery({ queryKey: ['search', query], queryFn: () => search(query) });

::: qa
Q: Czy dwa komponenty używające tego samego custom hooka współdzielą stan?
A: Nie. Custom hook współdzieli logikę; każde wywołanie tworzy własny stan. Wspólny stan wymaga Context, store'a lub podniesienia stanu.
Q: Jakie są Rules of Hooks?
A: Wywołuj hooki tylko na najwyższym poziomie (nie w pętlach, warunkach, zagnieżdżonych funkcjach) i tylko z komponentów funkcyjnych lub innych hooków. React identyfikuje hooki po kolejności wywołań, więc musi być stała.

::: sources
- React: Reusing Logic with Custom Hooks | https://react.dev/learn/reusing-logic-with-custom-hooks
- React: Rules of Hooks | https://react.dev/reference/rules/rules-of-hooks

@topic react-rendering-strategies
title: CSR, SSR, SSG, ISR
level: mid
tags: CSR, SSR, SSG, ISR, Next.js, SEO
summary: Strategie różnią się tym, gdzie i kiedy powstaje HTML: w przeglądarce (CSR), na serwerze przy każdym żądaniu (SSR), podczas buildu (SSG) lub podczas buildu z okresowym odświeżaniem (ISR).

::: body
| | Gdzie/kiedy HTML | Zalety | Wady | Przykład |
|---|---|---|---|---|
| **CSR** | przeglądarka, po pobraniu JS | prosty hosting, bogata interaktywność | pusty HTML na starcie, słabsze SEO i LCP | panel admina, dashboard za logowaniem |
| **SSR** | serwer, przy każdym żądaniu | aktualne dane, dobre SEO i FCP | koszt serwera, TTFB zależy od danych | wyniki wyszukiwania, personalizacja |
| **SSG** | build | najszybsze (CDN), tanie | dane aktualne tylko na moment buildu | blog, dokumentacja, landing |
| **ISR** | build + regeneracja w tle co X s lub na żądanie | szybkość SSG + świeższe dane | chwilowo nieaktualne dane, złożoność cache | karty ofert, katalog produktów |

W Next.js App Router strategia wynika z konfiguracji cache i danych: strony są statyczne, dopóki nie użyjesz dynamicznych API (cookies, headers, searchParams) lub nie wyłączysz cache. **Streaming SSR** z `Suspense` wysyła HTML w kawałkach: szybkie części od razu, wolne później. **Partial Prerendering / Cache Components** łączą statyczną "skorupę" strony z dynamicznymi fragmentami.

::: qa
Q: Czym różni się SSR od SSG?
A: SSR generuje HTML na serwerze przy każdym żądaniu (aktualne, spersonalizowane dane, wyższy koszt i TTFB). SSG generuje HTML raz, w czasie buildu, i serwuje go z CDN (bardzo szybkie, ale dane z momentu buildu).
Q: Czym jest ISR?
A: Incremental Static Regeneration: strona jest statyczna, ale po upływie czasu `revalidate` lub po wywołaniu revalidacji na żądanie Next.js generuje nową wersję w tle. Użytkownicy dostają szybką stronę z CDN i dane odświeżane cyklicznie.
Q: Którą strategię wybrać dla strony oferty wycieczki?
A: Najczęściej ISR lub SSG z revalidacją na żądanie: treść oferty zmienia się rzadko, a SEO i LCP są kluczowe. Dynamiczne elementy (cena na dziś, dostępność, koszyk) doładowujesz osobno (streaming lub klient). Za: szybkość i niski koszt. Przeciw: ryzyko chwilowo nieaktualnych danych, które trzeba zweryfikować przy rezerwacji.

::: sources
- web.dev: Rendering on the Web | https://web.dev/articles/rendering-on-the-web
- Next.js: Incremental Static Regeneration | https://nextjs.org/docs/app/guides/incremental-static-regeneration
- Next.js: Caching (Cache Components) | https://nextjs.org/docs/app/getting-started/caching

@topic react-hydration
title: Hydration
level: mid
tags: hydration, SSR, hydrateRoot, mismatch
summary: Hydration to "ożywienie" HTML-a wygenerowanego na serwerze: React w przeglądarce podpina event handlery i stan do istniejącego DOM, zamiast budować go od nowa.

::: body
1. Serwer renderuje HTML i wysyła go. Użytkownik od razu widzi treść (dobre FCP, LCP).
2. Przeglądarka pobiera JS.
3. React renderuje komponenty ponownie w pamięci i **dopasowuje** wynik do istniejącego DOM, podpinając zdarzenia. Od tej chwili strona jest interaktywna.

**Hydration mismatch**: HTML z serwera różni się od pierwszego renderu na kliencie. Przyczyny: `Date.now()`, `Math.random()`, `window`/`localStorage` w renderze, różna strefa czasowa lub locale, niepoprawne zagnieżdżenie HTML (`<div>` w `<p>`), rozszerzenia przeglądarki. Rozwiązania: wartości zależne od klienta ustawiaj w `useEffect`, przekaż dane z serwera, `suppressHydrationWarning` dla pojedynczych przypadków.

**Selective hydration** (React 18+): z `Suspense` React hydratuje fragmenty niezależnie i priorytetyzuje te, z którymi użytkownik wchodzi w interakcję.

Koszt: hydration wymaga pobrania i wykonania JS dla całej strony, co wpływa na INP i TBT. Server Components ograniczają ilość JS do hydracji.

::: code tsx
// Causes a mismatch: server and client render different values
function Price() {
  return <span>{new Date().toLocaleTimeString()}</span>;
}

// Fix: render client-only values after mount
function ClientTime() {
  const [time, setTime] = useState<string | null>(null);
  useEffect(() => setTime(new Date().toLocaleTimeString()), []);
  return <span>{time ?? '--:--'}</span>;
}

::: qa
Q: Czym jest hydration?
A: Procesem, w którym React po stronie klienta przejmuje HTML wygenerowany przez serwer: renderuje drzewo w pamięci, dopasowuje je do istniejącego DOM i podpina event handlery, bez odtwarzania DOM od zera.
Q: Co powoduje hydration mismatch i jak go naprawić?
A: Różnica między HTML z serwera a pierwszym renderem klienta: losowe wartości, daty, dostęp do `window` lub `localStorage`, różne locale, błędny HTML. Naprawa: wartości klienckie ustawiać po montażu (`useEffect`), deterministyczny render, poprawny HTML.

::: sources
- React: hydrateRoot | https://react.dev/reference/react-dom/client/hydrateRoot
- web.dev: Rendering on the Web | https://web.dev/articles/rendering-on-the-web

@topic react-server-components
title: React Server Components
level: senior
tags: RSC, Server Components, use client, Next.js App Router
summary: Server Components renderują się tylko na serwerze i nie wysyłają swojego kodu do przeglądarki. Client Components ('use client') obsługują interaktywność i są hydratowane.

::: body
- **Server Component** (domyślnie w Next.js App Router): może być `async`, czytać bezpośrednio z bazy lub API, używać sekretów. Nie ma stanu, efektów ani event handlerów. Jego kod **nie trafia do bundla** klienta.
- **Client Component**: plik z dyrektywą `'use client'`. Może używać `useState`, `useEffect`, zdarzeń, API przeglądarki. Jest renderowany na serwerze (SSR) i hydratowany w przeglądarce.
- `'use client'` wyznacza **granicę**: wszystko importowane z takiego pliku też staje się kodem klienckim. Server Component może przekazać Client Componentowi serializowalne props lub inne Server Components jako `children`.
- **Server Functions / Server Actions** (`'use server'`): funkcje wywoływane z klienta, wykonywane na serwerze (np. obsługa formularzy).

To nie to samo co SSR: SSR dotyczy generowania HTML, RSC dotyczy tego, które komponenty w ogóle nie wysyłają JS do przeglądarki.

Wzorzec: Server Components jako "szkielet" z danymi, a małe Client Components jako "wyspy" interaktywności (np. przycisk "Dodaj do ulubionych"), osadzone możliwie nisko w drzewie.

::: code tsx
// app/offers/[id]/page.tsx - Server Component (default)
export default async function OfferPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const offer = await db.offer.findUnique({ where: { id } }); // runs only on the server
  return (
    <article>
      <h1>{offer.title}</h1>
      <FavoriteButton offerId={id} /> {/* small interactive island */}
    </article>
  );
}

// FavoriteButton.tsx
'use client';
export function FavoriteButton({ offerId }: { offerId: string }) {
  const [fav, setFav] = useState(false);
  return <button aria-pressed={fav} onClick={() => setFav(!fav)}>Ulubione</button>;
}

::: qa
Q: Czym różnią się Server Components od SSR?
A: SSR to technika generowania HTML na serwerze dla komponentów, które potem są hydratowane (ich JS trafia do przeglądarki). Server Components renderują się tylko na serwerze i ich kod w ogóle nie jest wysyłany do klienta. W Next.js oba mechanizmy działają razem.
Q: Kiedy komponent musi być Client Component?
A: Gdy używa stanu, efektów, event handlerów, API przeglądarki (`window`, `localStorage`) lub bibliotek, które tego wymagają. Resztę zostaw jako Server Components, żeby zmniejszyć bundle.
Q: Co oznacza 'use client' dla importów?
A: Dyrektywa oznacza granicę: ten moduł i wszystko, co importuje, staje się częścią bundla klienta. Dlatego granice stawia się nisko w drzewie, na małych interaktywnych komponentach.

::: sources
- React: Server Components | https://react.dev/reference/rsc/server-components
- React: 'use client' | https://react.dev/reference/rsc/use-client
- Next.js: Server and Client Components | https://nextjs.org/docs/app/getting-started/server-and-client-components
