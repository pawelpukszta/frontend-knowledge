[error-handling] high
T: Właściwa obsługa błędów
D: `try/catch` przy operacjach asynchronicznych, obsługa odrzuconych Promise, Error Boundaries w React, czytelne komunikaty dla użytkownika i logowanie błędów do monitoringu.
W: `fetch` nie odrzuca Promise przy odpowiedziach 404 czy 500; bez sprawdzenia `response.ok` aplikacja próbuje parsować stronę błędu jako dane i pokazuje puste wyniki zamiast komunikatu.
W: Nieobsłużony błąd w komponencie React odmontowuje całe drzewo; bez Error Boundary użytkownik widzi białą stronę w środku procesu rezerwacji.
W: Błędy zgłaszane do monitoringu (np. Sentry) z kontekstem (`cause`, trasa, ID rezerwacji) pozwalają naprawić problem, zanim zgłosi go klient.
V: Wymuś błędy API (DevTools Network: blokowanie zapytań, nadpisanie odpowiedzi na 500, tryb offline) i sprawdź, czy UI pokazuje komunikat z możliwością ponowienia.
```ts
export async function getOffers(signal?: AbortSignal): Promise<Offer[]> {
  const res = await fetch("/api/offers", { signal });
  if (!res.ok) {
    // fetch resolves on HTTP errors, so throw explicitly
    throw new Error(`Offers request failed: ${res.status}`, { cause: res });
  }
  return OffersSchema.parse(await res.json());
}

// Last-resort reporting for anything not caught elsewhere
window.addEventListener("unhandledrejection", (event) => {
  reportError(event.reason);
});
```
```tsx React: granica błędu
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  fallback={<p role="alert">Nie udało się wczytać ofert. Odśwież stronę.</p>}
  onError={(error) => reportError(error)}
>
  <OfferList />
</ErrorBoundary>
```
X: Pusty `catch {}`, który połyka błąd bez logowania i bez informacji dla użytkownika.
X: Pokazywanie użytkownikowi surowego `error.message` ze stosu technicznego.

[javascript-inline] high
T: Bez skryptów inline
D: Kod w zewnętrznych plikach jest cache'owany, łatwiejszy w utrzymaniu i pozwala na restrykcyjne CSP bez `unsafe-inline`. Wyjątki obsłuż przez nonce.
W: CSP z `'unsafe-inline'` praktycznie nie chroni przed XSS, bo wstrzyknięty `<script>` lub `onerror=` wykona się tak samo jak Twój kod.
W: Atrybuty `onclick=` mieszają logikę z HTML, działają w zasięgu globalnym i nie da się ich testować ani sprawdzać linterem.
W: Zewnętrzny plik z hashem w nazwie może być cache'owany długo (`immutable`), a skrypt inline jest pobierany z każdą stroną.
V: Wyszukaj `<script>` bez `src` i atrybuty `on*=` w HTML; w konsoli sprawdź naruszenia CSP po włączeniu nagłówka w trybie `Content-Security-Policy-Report-Only`.
```html Źle
<button onclick="addToCart(1234)">Dodaj</button>
<script>window.config = { apiUrl: "/api" };</script>
```
```html Dobrze
<button type="button" data-offer-id="1234" class="js-add-to-cart">Dodaj</button>
<script type="application/json" id="app-config">{ "apiUrl": "/api" }</script>
<script type="module" src="/assets/app.3f9c2a.js"></script>
<!-- Unavoidable inline script: nonce generated per request -->
<script nonce="r4nd0mN0nc3">/* analytics bootstrap */</script>
```
```http
Content-Security-Policy: script-src 'nonce-r4nd0mN0nc3' 'strict-dynamic'; object-src 'none'; base-uri 'none'
```
X: Stała wartość nonce wpisana w szablon; nonce musi być losowy dla każdego żądania.

[console-cleanup] medium
T: Bez console.log na produkcji
D: Logi zaśmiecają konsolę, mogą ujawniać dane i spowalniać kod. Usuwaj je w buildzie (np. opcja minifiera) lub regułą `no-console`.
W: `console.log(user)` może pokazać w konsoli e-mail, numer telefonu czy token każdemu, kto otworzy DevTools, także na cudzym komputerze.
W: Logowanie dużych obiektów w pętli lub przy przewijaniu trzyma do nich referencje i spowalnia stronę, gdy DevTools są otwarte.
W: Konsola pełna szumu ukrywa prawdziwe ostrzeżenia (React, CSP, deprecjacje), które należałoby zauważyć.
V: Otwórz konsolę na produkcji podczas typowych działań (wyszukiwanie, rezerwacja); w CI `eslint --max-warnings 0` z regułą `no-console`.
```ts next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  compiler: {
    // Strip console.* in production builds, keep errors and warnings
    removeConsole: process.env.NODE_ENV === "production" ? { exclude: ["error", "warn"] } : false,
  },
};
export default nextConfig;
```
```js eslint.config.js (fragment)
rules: {
  "no-console": ["warn", { allow: ["warn", "error"] }],
},
```
X: Usuwanie logów zamiast zastąpienia ich prawdziwym monitoringiem błędów.

[javascript-linter] medium
T: Linter dla JavaScript
D: ESLint (z typescript-eslint, regułami React Hooks, jsx-a11y) wykrywa błędy, zanim trafią do code review. Uruchamiany w edytorze, pre-commit i CI.
W: Reguły React Hooks wyłapują brakujące zależności `useEffect` i warunkowe wywołania hooków, które dają trudne do odtworzenia błędy.
W: Reguły z informacją o typach (np. `no-floating-promises`) znajdują nieobsłużone Promise, czyli ciche błędy w produkcji.
W: Automatyczne reguły zwalniają code review z dyskusji o oczywistościach i pozwalają skupić się na logice i architekturze.
V: Krok lint w pipeline CI (`eslint . --max-warnings 0`) i lint-staged w pre-commit; od ESLint 9 konfiguracja w formacie flat (`eslint.config.js`).

[es-modules] high
T: Moduły ES (import/export)
D: Statyczne importy umożliwiają tree shaking, analizę zależności i lepsze narzędzia. CommonJS tylko tam, gdzie wymaga go środowisko.
W: Bundler zna strukturę `import`/`export` przed uruchomieniem kodu, więc może usunąć nieużywane eksporty; z `require()` musi dołączyć cały moduł.
W: ESM jest standardem przeglądarek i Node.js (22/24 LTS), a Node od wersji 22.12 pozwala nawet na `require()` modułów ESM, co ułatwia migrację.
W: Statyczne importy pozwalają edytorom i TypeScriptowi bezpiecznie zmieniać nazwy i znajdować nieużywany kod.
V: Przegląd `package.json` (`"type": "module"`, pole `exports`) i importów; wyszukaj `require(` i `module.exports` w kodzie aplikacji.
```js Źle
const _ = require("lodash"); // pulls the whole library
module.exports = { formatPrice };
```
```js Dobrze
import { debounce } from "lodash-es"; // tree-shakeable named import
export function formatPrice(amount) {
  return new Intl.NumberFormat("pl-PL", { style: "currency", currency: "PLN" }).format(amount);
}
```
```json package.json
{
  "type": "module",
  "exports": { ".": "./dist/index.js" },
  "sideEffects": false
}
```
X: Barrel files (`index.ts` reeksportujące wszystko), które utrudniają tree shaking i spowalniają build.

[translation-strings] medium
T: Teksty przyjazne tłumaczeniom
D: Używaj formatów komunikatów (ICU MessageFormat) z parametrami zamiast sklejania zdań z kawałków; kolejność słów różni się między językami.
W: Polski ma kilka form liczby mnogiej (1 oferta, 2 oferty, 5 ofert, 22 oferty); warunek `count === 1 ? 'oferta' : 'oferty'` daje błędy już dla 5 i 12.
W: Sklejanie `"Znaleziono " + n + " ofert w " + city` uniemożliwia tłumaczowi zmianę szyku zdania, a w wielu językach jest on inny.
W: `Intl.NumberFormat`, `Intl.DateTimeFormat` i `Intl.PluralRules` są wbudowane w przeglądarkę i poprawnie formatują ceny w PLN, daty i liczebniki.
V: Wyszukaj konkatenację tekstów UI (`+` lub szablony z tekstem) w kodzie; przetestuj liczby 0, 1, 2, 5, 12, 22 i 1,5.
```json messages/pl.json
{
  "results": "{count, plural, one {Znaleziono # ofertę} few {Znaleziono # oferty} many {Znaleziono # ofert} other {Znaleziono # oferty}} w {city}"
}
```
```ts
// Built-in formatting, no manual string building
const price = new Intl.NumberFormat("pl-PL", { style: "currency", currency: "PLN" }).format(12999);
// "12 999,00 zł" (with a non-breaking space as the group separator)
const date = new Intl.DateTimeFormat("pl-PL", { dateStyle: "long" }).format(new Date("2026-07-14"));
// "14 lipca 2026"
new Intl.PluralRules("pl-PL").select(5); // "many"
```
X: Tłumaczenie fragmentów zdań osobno ("Znaleziono", "ofert", "w") i składanie ich w kodzie.

[immutable-patterns] medium
T: Niemutowalne aktualizacje danych
D: Spread, `map`, `filter`, `toSorted`, `with` zamiast mutacji. Przewidywalny stan i poprawne działanie React (porównywanie referencji).
W: React, React Compiler i `memo` porównują referencje; po `state.push()` tablica jest ta sama, więc komponent się nie przerenderuje i UI pokazuje stare dane.
W: `sort()` i `reverse()` mutują tablicę w miejscu; posortowanie ofert po cenie w jednym komponencie zmienia kolejność w każdym innym, który dzieli te dane.
W: Niemutowalne aktualizacje ułatwiają debugowanie (poprzedni stan nadal istnieje) i funkcje typu cofnij.
V: Reguły lint lub code review pod kątem `push`, `splice`, `sort`, przypisań do pól stanu; React DevTools pokazuje, czy komponent się odświeżył.
```ts Źle
function onAdd(room: Room) {
  rooms.push(room);           // mutates state, no re-render
  setRooms(rooms);
}
const cheapest = offers.sort((a, b) => a.price - b.price); // mutates shared array
```
```ts Dobrze
setRooms((prev) => [...prev, room]);
const cheapest = offers.toSorted((a, b) => a.price - b.price);
const updated = rooms.with(index, { ...rooms[index], guests: 3 });
setBooking((b) => ({ ...b, contact: { ...b.contact, email } }));
```
X: Płytka kopia (`{ ...obj }`) przy zagnieżdżonych danych, a potem mutacja obiektu wewnątrz.

[modern-array-methods] medium
T: Nowoczesne metody tablic i obiektów
D: `map`, `filter`, `find`, `some`, `Object.entries`, `Object.groupBy`, `at()`, `structuredClone` zamiast ręcznych pętli i bibliotek pomocniczych.
W: Deklaratywne metody mówią, co kod robi (`filter`, `some`), zamiast jak; mniej zmiennych pomocniczych to mniej błędów indeksów.
W: `structuredClone` poprawnie kopiuje głęboko obiekty z `Date`, `Map`, `Set` i cyklami, czego nie robi `JSON.parse(JSON.stringify())`.
W: Wbudowane `Object.groupBy`, `toSorted` czy metody `Set` (Baseline 2024) pozwalają usunąć zależności od lodash i zmniejszyć bundle.
V: Przegląd kodu; reguły z eslint-plugin-unicorn (np. `prefer-at`, `no-for-loop`) i sprawdzenie celu `browserslist`/`target` dla nowszych metod.
```ts
const byCountry = Object.groupBy(offers, (o) => o.country); // { Grecja: [...], Hiszpania: [...] }
const last = offers.at(-1);
const hasLastMinute = offers.some((o) => o.tags.includes("last-minute"));
const draft = structuredClone(booking); // deep copy, keeps Date objects
const shared = new Set(myFavs).intersection(new Set(promoIds));
for (const [code, price] of Object.entries(pricesByCode)) {
  console.info(code, price);
}
```
X: `forEach` z `async` callbackiem, który nie czeka na zakończenie operacji; użyj `for...of` z `await` lub `Promise.all`.

[const-let] high
T: const i let zamiast var
D: Zasięg blokowy i TDZ eliminują błędy wynikające z hoistingu `var`. Domyślnie `const`, `let` tylko dla zmiennych zmieniających wartość.
W: `var` ma zasięg funkcji, więc zmienna z pętli jest jedna dla wszystkich iteracji; klasyczny błąd to kilka handlerów, które widzą tylko ostatnią wartość.
W: Odczyt `let`/`const` przed deklaracją rzuca `ReferenceError` (TDZ), zamiast po cichu zwracać `undefined` jak `var`.
W: `const` sygnalizuje czytelnikowi, że referencja się nie zmieni, co ułatwia analizę kodu (choć zawartość obiektu nadal można mutować).
V: ESLint (`no-var`, `prefer-const`), obie reguły z automatyczną poprawką `--fix`.
```js Źle
for (var i = 0; i < buttons.length; i++) {
  buttons[i].addEventListener("click", () => select(i)); // always the last i
}
console.log(total); // undefined, no error
var total = 100;
```
```js Dobrze
for (let i = 0; i < buttons.length; i++) {
  buttons[i].addEventListener("click", () => select(i)); // i per iteration
}
const total = 100;
let remaining = total;
remaining -= 20;
```
X: `const` dla obiektu w przekonaniu, że jest niemutowalny; do tego służy `Object.freeze` lub `as const` w TypeScript.

[type-coercion] medium
T: Bez niejawnej konwersji typów
D: `===` zamiast `==`, jawne `Number()`, `String()`, `Boolean()`. Niejawna koercja prowadzi do błędów typu `'5' + 1 === '51'`.
W: Wartości z pól formularza i parametrów URL są stringami; `guests + 1` dla `"2"` daje `"21"` gości.
W: Reguły `==` są nieintuicyjne: `0 == ''`, `'0' == false` i `null == undefined` są prawdziwe, co psuje warunki walidacji.
W: Jawna konwersja wymaga decyzji o błędnych danych: `Number('')` to `0`, a `Number('abc')` to `NaN`; trzeba je obsłużyć świadomie.
V: ESLint (`eqeqeq`, ewentualnie z opcją `{ null: "ignore" }`) i TypeScript, który zgłasza dodawanie liczby do stringa w wielu przypadkach.
```js Źle
const guests = form.guests.value + 1;        // "21"
if (searchParams.get("page") == 0) { /* true for "" and "0" */ }
```
```js Dobrze
const guests = Number.parseInt(form.guests.value, 10);
if (!Number.isInteger(guests) || guests < 1) throw new RangeError("Invalid guests count");

const page = Number(searchParams.get("page") ?? "1");
if (page === 1) { /* strict comparison */ }
const label = String(price); // explicit conversion
```
X: Sprawdzanie `if (value)` dla liczb, gdzie `0` jest poprawną wartością (np. 0 zł dopłaty).

[typescript-strict-mode] high
T: TypeScript w trybie strict
D: `"strict": true` włącza m.in. `strictNullChecks` i `noImplicitAny`, które wyłapują całe klasy błędów runtime w czasie kompilacji.
W: Bez `strictNullChecks` typ `User` może być w rzeczywistości `null`, a "Cannot read properties of undefined" to jeden z najczęstszych błędów JS w produkcji.
W: Od TypeScript 6.0 `strict` jest domyślnie włączony, ale starsze projekty i skopiowane konfiguracje często mają `false`; zapisz go jawnie.
W: Włączenie strict w dojrzałym projekcie jest kosztowne, więc warto to zrobić od początku albo migrować katalog po katalogu.
V: Sprawdź `tsconfig.json` i krok `tsc --noEmit` w CI; build nie może przechodzić z błędami typów.
```json tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,
    "target": "es2023",
    "module": "esnext",
    "moduleResolution": "bundler",
    "skipLibCheck": true
  }
}
```
X: `// @ts-ignore` zamiast naprawy typu; jeśli musisz, użyj `// @ts-expect-error` z komentarzem.
S: TSConfig: strict | https://www.typescriptlang.org/tsconfig/#strict

[type-only-imports] low
T: import type dla importów samych typów
D: `import type { User }` gwarantuje usunięcie importu przy kompilacji (ważne przy izolowanej transpilacji esbuild/SWC i `verbatimModuleSyntax`).
W: Narzędzia transpilujące plik po pliku (esbuild, SWC, Babel) nie wiedzą, czy importowana nazwa jest typem; bez `import type` import może zostać w JS i wywołać błąd lub zbędny efekt uboczny.
W: Node.js 24 (oraz 22 od wersji 22.18) uruchamia pliki `.ts` przez usuwanie typów; import typu bez słowa `type` kończy się błędem, bo moduł nie ma takiego eksportu w runtime.
W: Czytelnik od razu widzi, które zależności są tylko typami, a które naprawdę trafiają do bundla.
V: typescript-eslint (`consistent-type-imports`) z autopoprawką oraz `verbatimModuleSyntax: true` w `tsconfig.json`.
```ts Źle
import { Booking, createBooking } from "./booking"; // Booking is only a type
```
```ts Dobrze
import type { Booking } from "./booking";
import { createBooking } from "./booking";
// or inline:
import { createBooking, type Booking } from "./booking";
```
X: Inline `type` przy wszystkich nazwach (`import { type A, type B }`), co z `verbatimModuleSyntax` zostawia pusty import z efektami ubocznymi; wtedy użyj `import type`.

[runtime-validation] high
T: Walidacja danych zewnętrznych w runtime
D: Typy TS znikają po kompilacji, więc odpowiedzi API, formularze, localStorage i parametry URL waliduj schematem (Zod, Valibot) i z niego wyprowadzaj typy.
W: `await res.json() as Offer[]` to tylko obietnica; gdy backend zmieni `price` na string, błąd wybuchnie daleko od źródła, np. przy formatowaniu ceny.
W: Jeden schemat daje walidację i typ (`z.infer`), więc typ nie rozjedzie się z rzeczywistą kontrolą.
W: Walidacja na granicy systemu chroni też przed złośliwymi danymi z URL czy `postMessage`; po stronie serwera jest obowiązkowa niezależnie od walidacji w przeglądarce.
V: Przegląd granic systemu: czy dane z `fetch`, `JSON.parse`, `FormData` i `URLSearchParams` przechodzą przez `parse`/`safeParse`.
```ts
import { z } from "zod";

export const OfferSchema = z.object({
  id: z.string(),
  hotel: z.string().min(1),
  price: z.number().positive(),
  departure: z.iso.date(),
  board: z.enum(["BB", "HB", "AI"]),
});
export type Offer = z.infer<typeof OfferSchema>;

const SearchSchema = z.object({ adults: z.coerce.number().int().min(1).max(9) });
const result = SearchSchema.safeParse(Object.fromEntries(new URLSearchParams(location.search)));
const adults = result.success ? result.data.adults : 2; // safe default
```
X: Rzutowanie `as` na danych z sieci zamiast parsowania.
S: Zod | https://zod.dev/

[no-explicit-any] medium
T: Bez typu any
D: `any` wyłącza sprawdzanie typów i "zaraża" kolejne wartości. Zamiast tego `unknown` z zawężaniem, generyki lub konkretne typy.
W: Każda wartość wyprowadzona z `any` też jest `any`, więc jeden niedookreślony parametr wyłącza kontrolę typów w całym łańcuchu wywołań.
W: `unknown` zmusza do sprawdzenia typu przed użyciem, np. w bloku `catch`, gdzie błąd nie musi być obiektem `Error`.
W: Refaktoryzacja z `any` jest ryzykowna: kompilator nie wskaże miejsc, które przestały pasować.
V: typescript-eslint (`no-explicit-any`, a z regułami z typami także `no-unsafe-assignment`, `no-unsafe-member-access`).
```ts Źle
function getTotal(data: any) {
  return data.items.reduce((sum: any, i: any) => sum + i.price, 0);
}
```
```ts Dobrze
function getTotal(items: readonly { price: number }[]): number {
  return items.reduce((sum, i) => sum + i.price, 0);
}
function toMessage(error: unknown): string {
  return error instanceof Error ? error.message : String(error);
}
function first<T>(list: readonly T[]): T | undefined {
  return list[0];
}
```
X: Zastępowanie `any` przez `as unknown as Foo`, co jest tym samym obejściem w innym przebraniu.

[no-unchecked-indexed-access] medium
T: noUncheckedIndexedAccess
D: Dostęp `arr[i]` i `record[key]` ma typ `T | undefined`, co wymusza obsłużenie braku wartości.
W: Bez tej flagi `prices[code]` ma typ `number`, nawet gdy klucza nie ma; błąd ujawnia się dopiero jako `NaN` na stronie.
W: Flaga nie jest częścią `strict`, więc trzeba ją włączyć osobno.
W: Wymusza świadome decyzje: wartość domyślna, wczesny return albo komunikat o braku danych.
V: Sprawdź `tsconfig.json`; po włączeniu przejrzyj nowe błędy, bo wskazują realne miejsca potencjalnego `undefined`.
```ts
// tsconfig: "noUncheckedIndexedAccess": true
const surcharges: Record<string, number> = { SGL: 450, SEA: 120 };

function surchargeFor(code: string): number {
  const value = surcharges[code]; // number | undefined
  return value ?? 0;
}

const [firstOffer] = offers; // Offer | undefined
if (!firstOffer) return <EmptyState />;
```

[scheduler-yield] medium
T: scheduler.yield() przy długich zadaniach
D: Zadania dłuższe niż 50 ms blokują interakcje. Dziel pracę i oddawaj kontrolę przeglądarce przez `await scheduler.yield()` (z fallbackiem na `setTimeout`).
W: Podczas długiego zadania przeglądarka nie obsłuży kliknięcia ani nie narysuje klatki, co bezpośrednio pogarsza INP (próg dobrego wyniku 200 ms).
W: `scheduler.yield()` wznawia kod z wyższym priorytetem niż `setTimeout`, więc praca nie trafia na koniec kolejki za innymi zadaniami.
W: API nie jest Baseline (brak m.in. w Safari), dlatego fallback na `setTimeout` jest konieczny.
V: DevTools Performance: zadania oznaczone czerwonym trójkątem (Long task); po zmianie powinny być podzielone na krótsze kawałki.
```js
function yieldToMain() {
  if (globalThis.scheduler?.yield) return globalThis.scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}

async function renderOffers(offers) {
  let deadline = performance.now() + 50;
  for (const offer of offers) {
    renderOffer(offer);
    if (performance.now() > deadline) {
      await yieldToMain(); // let the browser handle input and paint
      deadline = performance.now() + 50;
    }
  }
}
```
X: Oddawanie kontroli po każdym elemencie przy tysiącach elementów; narzut wydłuża całą pracę, lepiej co ok. 50 ms.

[event-delegation] medium
T: Delegacja zdarzeń
D: Jeden listener na kontenerze zamiast setek na elementach listy: mniej pamięci i obsługa elementów dodanych dynamicznie.
W: Lista 500 ofert z osobnym listenerem na każdym przycisku to 500 funkcji w pamięci i dłuższe przypinanie przy każdym przerenderowaniu.
W: Elementy dociągnięte przy "pokaż więcej" automatycznie działają, bez ponownego podpinania handlerów.
W: Jedno miejsce obsługi akcji upraszcza sprzątanie: usunięcie jednego listenera zamiast śledzenia setek.
V: Przegląd kodu list i tabel; w DevTools Elements zakładka Event Listeners pokazuje, gdzie podpięto handlery.

[debounce-throttle] high
T: Debounce i throttle dla częstych zdarzeń
D: `input`, `scroll`, `resize`, `mousemove` mogą odpalać się dziesiątki razy na sekundę. Debounce dla wyszukiwania, throttle (lub `requestAnimationFrame`) dla przewijania.
W: Wyszukiwarka destynacji bez debounce wysyła zapytanie po każdej literze: "Bar", "Barc", "Barce"..., co obciąża API i może pokazać wyniki dla starszego zapytania.
W: Ciężki handler `scroll` uruchamiany przy każdym zdarzeniu blokuje główny wątek i pogarsza płynność oraz INP.
W: Dla wielu przypadków istnieją lepsze narzędzia niż throttle: `IntersectionObserver` do lazy loadingu, `ResizeObserver` do zmian rozmiaru.
V: Licznik wywołań handlera lub liczba zapytań w Network podczas szybkiego pisania; kolejność odpowiedzi przy symulacji wolnej sieci.
```ts
function debounce<A extends unknown[]>(fn: (...args: A) => void, ms = 300) {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return (...args: A) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

let controller: AbortController | undefined;
const search = debounce(async (query: string) => {
  controller?.abort(); // cancel the stale request
  controller = new AbortController();
  const res = await fetch(`/api/destinations?q=${encodeURIComponent(query)}`, { signal: controller.signal });
  renderSuggestions(await res.json());
}, 300);

input.addEventListener("input", (e) => search((e.target as HTMLInputElement).value));
```
X: Debounce tworzony wewnątrz komponentu React przy każdym renderze (nowa funkcja, nowy timer); trzymaj go w `useMemo` lub `useRef`.

[dom-performance] high
T: Grupowanie odczytów i zapisów DOM
D: Przeplatanie odczytów geometrii (`offsetHeight`) i zapisów stylów wymusza wielokrotny layout (layout thrashing). Najpierw odczyty, potem zapisy, najlepiej w `requestAnimationFrame`.
W: Każdy odczyt geometrii po zmianie stylu zmusza przeglądarkę do natychmiastowego przeliczenia layoutu; w pętli po 200 kartach to 200 pełnych layoutów zamiast jednego.
W: Wymuszone layouty wydłużają zadania na głównym wątku, przez co kliknięcia czekają, a INP rośnie.
W: Często lepiej w ogóle unikać odczytów w JS: CSS Grid, container queries lub `ResizeObserver` dostarczają tej samej informacji bez wymuszonego layoutu.

[avoid-eval] critical
T: Nigdy eval() ani new Function()
D: Wykonywanie kodu ze stringów otwiera drogę do XSS, uniemożliwia restrykcyjne CSP i optymalizacje silnika. Dotyczy też `setTimeout('string')`.
W: Jeśli do `eval` trafi choćby fragment danych od użytkownika lub z URL, atakujący wykonuje dowolny kod w kontekście zalogowanej sesji: kradnie dane, składa zamówienia.
W: Użycie `eval` wymaga `'unsafe-eval'` w CSP, co osłabia ochronę całej aplikacji, także w miejscach bez `eval`.
W: Silnik JS nie może zoptymalizować funkcji zawierającej `eval`, bo nie wie, jakie zmienne zostaną odczytane.

[json-safety] medium
T: Bezpieczne parsowanie JSON
D: `JSON.parse` rzuca wyjątek przy niepoprawnych danych; opakuj go w `try/catch` i zwaliduj strukturę wyniku (np. schematem).
W: Uszkodzony wpis w localStorage (np. po zmianie formatu w nowej wersji) z nieobsłużonym wyjątkiem potrafi zablokować start całej aplikacji.

```ts
import { z } from "zod";

export function safeJsonParse<T>(text: string | null, schema: z.ZodType<T>): T | null {
  if (text == null) return null;

    return result.success ? result.data : null;
  } catch {
    return null; // malformed JSON
  }
}
```

[web-storage] medium
T: Bezpieczne korzystanie z Web Storage
D: Odczyty i zapisy w `try/catch` (tryb prywatny, przekroczony limit), brak tokenów i danych wrażliwych, walidacja odczytanych danych.
W: Dostęp do `localStorage` może rzucić `SecurityError` (zablokowane dane witryn, iframe), a zapis `QuotaExceededError` po przekroczeniu limitu, zwykle ok. 5 MB na origin.
W: Każdy skrypt na stronie, także wstrzyknięty przez XSS lub skompromitowaną bibliotekę, czyta localStorage; tokeny sesji powinny być w ciasteczkach `HttpOnly`, `Secure`, `SameSite`.
W: `localStorage` jest synchroniczny i blokuje główny wątek; duże dane lepiej trzymać w IndexedDB.
V: Przegląd użycia `localStorage` i `sessionStorage`; DevTools Application: Storage, test z zablokowanymi danymi witryn i z uszkodzonym wpisem.
```ts
import { z } from "zod";
export const storage = {
  get<T>(key: string, schema: z.ZodType<T>): T | null {
    try {
      const raw = localStorage.getItem(key);
      const parsed = raw === null ? null : schema.safeParse(JSON.parse(raw));
      return parsed?.success ? parsed.data : null;
    } catch {
      return null; // storage blocked or malformed JSON
    }
  },
  set(key: string, value: unknown): boolean {
    try {
      localStorage.setItem(key, JSON.stringify(value));
      return true;
    } catch {
      return false; // QuotaExceededError or SecurityError
    }
  },
};
```
X: Trzymanie w localStorage tokenu JWT lub danych osobowych z formularza rezerwacji (PESEL, numer paszportu).
